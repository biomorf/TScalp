# AGENTS.md — директивы для ИИ-ассистента

Документ описывает правила работы ИИ-ассистента над проектом TScalp
(Android-приложение для торговли через T-Invest, BCS, Finam).
Читается в начале каждой сессии. Применяется без исключений,
кроме случаев, когда пользователь явно отменяет правило.

---

## Стиль работы

### 1. Не менять UI без санкции

Любое изменение, видимое пользователю (тексты, иконки, разметка,
порядок элементов, названия вкладок, цвета), требует явного
согласования **до** внесения правок. Ассистент описывает, что
собирается изменить, получает подтверждение, только затем пишет код.

Изменения в слое данных, логике, ViewModel, репозитории — не
требуют санкции. UI — требует.

### 2. Чистота кода — приоритет

Если для решения задачи требуется переделать что-то «как следует»,
и это больше объёма, чем минимальный фикс — ассистент **обязан**
предложить такой вариант явно. Объём работы не является аргументом
против чистого решения.

Ассистент всегда рассматривает оба варианта (минимальный фикс /
правильное решение) и предлагает пользователю выбрать. Молча
скатываться к костылю — запрещено.

### 2a. Актуальность решений, не традиция

При выборе инструмента, подхода или архитектурного решения
ассистент **обязан** рассматривать и предлагать не только
исторически привычный вариант, но и актуальное состояние
экосистемы на текущий момент.

Конкретно:

- **Проверять актуальность инструмента.** Прежде чем предлагать
  JaCoCo, Retrofit, Mockito, shared preferences, Dagger — ассистент
  проверяет, что это не устаревший дефолт, вытесненный более
  современным решением. Например, для Android/Kotlin в 2026 году:
  Kover вместо JaCoCo, Ktor/OkHttp вместо Retrofit, KSP вместо
  kapt, DataStore вместо SharedPreferences, Hilt (в проекте уже
  есть) вместо Dagger.
- **Не опираться на «так принято».** «Все так делают» — не
  аргумент. Аргумент — «это работает лучше/проще/надёжнее
  здесь и сейчас».
- **Явно указывать альтернативы.** Если есть 2–3 разумных
  варианта, ассистент перечисляет их, отмечает актуальный
  и объясняет выбор.
- **Признавать устаревшие установки.** Если ассистент поймёт,
  что предложил традиционное решение по инерции, а не по
  существу, — он говорит об этом прямо и предлагает
  пересмотреть.
- **Сверяться с датой.** Сессия идёт в 2026 году, не в 2020.
  «Стандарт де-факто» пятилетней давности может быть уже
  legacy.

Правило действует всегда: при выборе библиотек, паттернов,
структуры кода, инструментов CI, форматов данных. Не только
при явном обсуждении стека.

### 2b. Организационные практики — по индустрии

Правило 2a (актуальность решений) действует для прикладного
стека: библиотеки, паттерны, инструменты. Для
**организационного слоя** — CI/CD, ветвления, code review,
релизного цикла — действует отдельный принцип.

**Принцип:** организационные практики воспроизводятся по
актуальным индустриальным стандартам, **даже если часть из
них создаёт overhead сейчас и не имеет потребителя в
текущем масштабе проекта**.

**Почему:** организационный слой — задел под рост команды.
Когда появляется второй разработчик или тестировщик,
перестройка процесса на ходу дороже, чем изначально
воспроизвести индустриальную схему. Плюс: соло-разработка
на индустриальном процессе — это опыт воспроизведения
практики, применимый в командной работе.

**Что попадает под правило:**
- git-flow и стратегии merge (GitHub Flow / GitFlow /
  Trunk-Based);
- защита веток, правила PR, required checks;
- стадии CI-пайплайна (lint → build → test → deliver);
- публикация артефактов (Firebase, Play Store);
- code review через второй аккаунт (role emulation);
- secrets и окружения (Repository vs Environment).

**Как выбирается стандарт:**
- Если есть индустриальный стандарт де-факто (GitFlow,
  GitHub Flow, semantic versioning) — воспроизводим его.
- Если стандарты конкурируют (например, Squash vs Merge
  commit) — выбирается один осознанно, с обоснованием,
  фиксируется в `docs/`.
- Если стандарт конфликтует с текущей настройкой проекта
  (например, Merge commit у нас уже зафиксирован в ROADMAP,
  а GitFlow рекомендует Squash) — решение пересматривается
  явно, а не «оставляем как было».

**Отклонения от стандарта** допускаются, если они
**осознанные и задокументированы** (например, имя ветки
`dev` вместо `develop` — канон GitFlow, но миграция дороже,
чем отклонение). Каждое отклонение — отдельная строка в
`docs/git-flow.md` со ссылкой на причину.

**Не путать с правилом 2a:**
- 2a — «какой инструмент выбрать» (прикладное).
- 2b — «как организовать процесс» (организационное).

### 2c. Проверка решений на соответствие Clean-архитектуре

Целевая архитектура проекта — Clean (`presentation → domain →
data`, dependency rule внутрь, domain не знает о data и
платформе). Перед предложением или принятием решения ассистент
**обязан** явно проверить его на соответствие целевой Clean
и **проговорить** результат проверки.

Формат:

- **Соответствует:** одна строка — почему.
- **Не соответствует:** одна строка — какое именно правило
  Clean нарушено.
- **Альтернатива Clean:** если решение не соответствует —
  ассистент **обязан** предложить хотя бы одно альтернативное
  решение, соответствующее Clean, с плюсами и минусами, даже
  если пользователь уже принял несоответствующее решение.

**Пользователь принял решение — это не отменяет обязанности
проговорить несоответствие и альтернативу.** Решение
пользователя выполняется, но с явной пометкой «принято,
несмотря на нарушение Clean: <правило>» и со ссылкой на
альтернативу.

**Не путать с 3a/3b:** 3a/3b — про видимость дефолтов,
2c — про архитектурную дисциплину. Оба действуют
одновременно.

**Причина:** Clean-архитектура — не «пожелание на будущее»,
а текущая цель. Решение, противоречащее ей, накапливает
долг, который проявится позже. Явная фиксация
несоответствия в момент принятия — единственная точка,
где долг можно остановить.


**Фиксация отклонения — обязательные элементы.**

При фиксации отклонения от Clean (в коде, KDoc, ROADMAP,
AGENTS.md) все три элемента обязательны:

1. **Правило Clean, которое нарушено.** Одна строка.
2. **Clean-альтернатива.** Что было бы сделано по Clean —
   с плюсами и минусами.
3. **Выгоды выбранного варианта относительно альтернативы.**
   Почему выбранный вариант лучше **для этого проекта
   сейчас**, даже если нарушает Clean. Конкретно: что
   экономит (время / строки / риск), что упрощает, что
   становится возможным.

Без третьего элемента фиксация неполная: «принято,
несмотря на нарушение Clean: <правило>. Альтернатива:
<вариант>» — констатирует отклонение, но не объясняет
решение. Читатель через полгода не поймёт, почему
отклонились.

**Причина:** отклонение без обоснования — потерянный
контекст. Следующая сессия видит «принято, несмотря на
нарушение» и не понимает, зачем переделывать. Фиксация
выгод — защита от повторного обсуждения того же вопроса.

**Уточнения между уровнями clean-audit.** Запись
`docs/clean-audit.md` одного уровня может быть уточнена
анализом другого уровня (переформулировка, расширение
области, подтверждение или опровержение гипотезы).
Уточнение фиксируется явно — в самой записи, в ROADMAP,
KDoc или commit message — в формате:

- «подтверждается анализом уровня L<N>-<ID>: <что именно>»;
- «опровергается анализом уровня L<N>-<ID>: <что именно>».

`L<N>` — уровень (`L1`..`L8`), `<ID>` — идентификатор
записи (`Н21`, `Н29`, …). Формат работает для двух случаев:
- **Cross-level:** `L<N>-<ID>` — уточнение записи одного
  уровня анализом другого (`L1-Н22` уточнена `L7-Н29`).
- **Same-level, part-K:** `L<N>-part<K>` — уточнение записи
  тем же уровнем, но в другой части аудита (`L4-part2`
  уточняет `Н25` из `L4-part1`). Используется, когда
  уровень проверяется по частям (вариант B аудита:
  `L4-part1`, `L4-part2`, …).

Формат блока в записи clean-audit:

    **Анализ L<N>-<ID>:** подтверждается / опровергается —
    <что именно подтверждено или опровергнуто>.

Блок `**Анализ L<N>-<ID>:**` — опциональный (только если
запись уточняется анализом другого уровня). При правке
записи из другого уровня блок добавляется в конец
существующей записи, перед полем `**Ссылка на задачу:**`.

**Причина:** одна проблема может проявляться на нескольких
уровнях (например, `BrokerManager` — L7, но нарушение
dependency rule в presentation — L1; уточнение L1-Н22
приходит из анализа L7-Н29). Без явной ссылки читатель
не понимает, откуда уточнение, и в следующей сессии может
откатить правку или завести дубль.

**Clean-audit — полная инвентаризация.** Каждая находка
(нарушение Clean, presentation-текст в нижнем слое, god-класс,
`@Suppress` как маркер долга, swallowed exception, dead code,
дублирование) заводится **отдельной записью** в
`docs/clean-audit.md`. Существование задачи в
`docs/ROADMAP.md` / `docs/ci-roadmap.md` / записи в
`docs/ISSUES.md` **не является поводом не заводить запись** —
наоборот, запись в clean-audit должна содержать
`**Ссылка на задачу:**` с указанием на эту задачу/запись.

**Причина:** задачи в ROADMAP могут быть отменены,
переформулированы или объединены. Записи в ISSUES — отражать
симптом, а не архитектурную природу. Если находка не
зафиксирована в clean-audit отдельно, при изменении
ROADMAP/ISSUES она исчезает из инвентаризации. Clean-audit —
единственная точка, где каждая находка сохраняется
независимо от судьбы задачи.

### 2d. Временные решения явно маркируются и закрываются задачей

Если при планировании или реализации принимается половинчатое,
пробное или временное решение (костыль, обходной путь, заглушка,
«пока так, потом переделаем»), ассистент **обязан**:

1. Явно проговорить, что решение временное, и почему.
2. Явно проговорить, каким будет полное решение.
3. В `docs/ROADMAP.md` (или `docs/ISSUES.md` для проблем)
   в **той же сессии** создать задачу, закрывающую вопрос
   полным образом — с полями по 5e.
4. Если это код — оставить в нём маркер (`TODO` с ссылкой
   на задачу ROADMAP или KDoc-пометку).

Запрещено принимать временное решение молча, без задачи
на полное. Временное решение без задачи — потерянный долг:
следующая сессия не вспомнит, что «пока так» значит
«потом переделать».

**Не путать с 2:** 2 — выбор между минимальным фиксом и
правильным решением (оба предлагаются). 2d — что делать,
если пользователь выбрал минимальный/временный вариант.

**Не путать с «Запрещено оставлять TODO без согласования»:**
там — про сам факт TODO; здесь — про процесс его появления
и обязательное закрытие задачей в ROADMAP.


### 3. Не выдумывать

Если ассистент не может подтвердить факт (не видит файла,
не знает содержимого ссылки, не уверен в поведении API) — он
говорит об этом прямо. Запрещено генерировать правдоподобные
догадки и выдавать их за факты.

Формулировки «я изучил», «я увидел», «судя по вашим файлам»
допустимы только тогда, когда содержимое действительно было
передано в текущей сессии.

### 3a. Явные дефолты при неполном ответе

Когда ассистент задаёт серию вопросов (Q1, Q2, …), а пользователь
отвечает не на все, — ассистент принимает решение по неотвеченным
и **явно перечисляет принятые дефолты** отдельным блоком.

Формат:

    **Дефолты** (не уточнено пользователем):
    - Q2: <значение> — <обоснование одной строкой>
    - Q4: <значение> — <обоснование одной строкой>

Правило действует и вне Q-серий: когда ассистент принимает решение
за пользователя (неоднозначная формулировка, стандартный паттерн
без явного выбора) — решение помечается так же явно.

**Зачем:** длинная серия вопросов + частичный ответ = решения
тонут в переписке. Явное перечисление даёт точку проверки:
пользователь может отменить или скорректировать дефолт **до**
того, как код написан. Без этого приходится перечитывать чат
и восстанавливать, что решили «по умолчанию».

**Не путать с 4b:** 4b — про количество шагов в ответе;
3a — про видимость принятых решений. Оба действуют одновременно.

### 3b. Дефолты не считаются утверждёнными

Любое решение, принятое ассистентом за пользователя (см. 3a),
имеет статус **«предложено»**, а не «утверждено». До явного
«да» / «ок» / «принимаю» от пользователя:

- ассистент **повторяет** список дефолтов в начале каждого
  следующего ответа, пока они не утверждены или не отменены;
- ассистент **не переходит к следующему шагу**, если текущий
  шаг опирается на неутверждённый дефолт;
- если пользователь отвечает на часть вопросов, а по остальным
  молчит — дефолты по неотвеченным остаются «предложенными»
  и повторяются.

Формат повтора:

    **Неутверждённые дефолты:**
    - Q<n>: <значение> — статус: предложено, жду подтверждения.

После явного «да» дефолт переходит в «утверждено» и больше
не повторяется (но остаётся в силе).

**Зачем:** молчаливое принятие дефолта — решение, о котором
пользователь не помнит. Повтор даёт точку контроля до того,
как на дефолте построен следующий шаг.


### 4. Маленькие шаги с проверкой

Одна задача — один логически завершённый шаг. Между шагами —
сборка (`./gradlew :app:clean :app:testDebugUnitTest --rerun-tasks \
      2>&1 | grep -E '\[warn\]|\[error\]|^w:|^e:'`)
и проверка, что тесты зелёные и новых ошибок компиляции нет.
Фильтр `grep` нужен, потому что Gradle 9.x показывает
Kotlin compiler warnings через Problems API (HTML-отчёт +
секция `[warn]`) вместо привычного `w: file:///`. Без фильтра
warning'и тонут в служебном выводе. Проверяем, что тесты зелёные
и новых ошибок компиляции нет.

Крупные задачи дробятся на подшаги. Например: добавить метод в
репозиторий → скомпилировать → мигрировать вызывающего →
скомпилировать → удалить старый метод → скомпилировать.

Если задача слишком большая для одного сообщения — ассистент
предлагает разбивку, не пытается выдать всё сразу.

### 4a. Формат показа правок

Правки кода показываются в формате **«было → стало»**, не diff'ом.
Diff'ы неудобны для чтения с телефона и требуют мысленного
восстановления контекста.

Формат:

**Файл:** `путь/к/файлу.kt`, строка N

**Было:**
```kotlin
<старый фрагмент>
```
**Стало:**
```kotlin
<новый фрагмент>
```
Если правка мелкая (одна строка, замена имени) — «было-стало»
в одну строку через → допустимо.

**Одна правка — один блок.** Если правок несколько (даже в
одном файле), каждая выводится отдельным блоком «было →
стало» со своим заголовком «Файл: ... строка N». Сводный
блок с несколькими заменами («Было (три места): ...») —
запрещён.

Причина: пользователь читает с телефона и проверяет правки
по одной. Общий блок снижает контроль и повышает риск
пропустить расхождение между показом и применением.

**Защита от случайного запуска в терминале.**
Каждый блок «Стало» оборачивается в heredoc no-op:

    : <<'STALO_END'
    <содержимое «Стало»>
    STALO_END

Если пользователь вставит блок в терминал целиком — bash
прочитает содержимое в no-op `:` и ничего не выполнит. Это
защита от инцидента 2026-10-20/21 (см. 4e).

**Автоматический критерий «короткая / длинная»:**

- **Короткая:** меньше 20 строк И без fence `~~~yaml`,
  `~~~bash`, `~~~shell`, `~~~sh` внутри «Стало».
- **Длинная:** 20+ строк ИЛИ есть хотя бы один такой fence.

**Короткая правка:** показывается «было → стало» с
«Стало» в heredoc-обёртке, скрипт применения — до «Стало».

**Длинная правка:** «Стало» не показывается. Вместо него:

1. Summary — 1–3 предложения: что добавляется, куда,
   сколько строк.
2. Маркер-якорь — 2–3 строки контекста до/после места
   вставки.
3. Скрипт применения.

Причина: инцидент 2026-10-20/21. Markdown-блок 143 строки
с `~~~yaml` был вставлен в терминал целиком, bash выполнил
`git push --mirror` из YAML-примера.

**Порядок блоков в ответе:**

1. Объяснение (1–3 предложения).
2. «Было» / summary + маркер (для длинной).
3. Скрипт применения.
4. «Стало» в heredoc-обёртке (только для короткой,
   после скрипта).

Скрипт — всегда **до** «Стало», чтобы копировался первым.

При массовых однотипных правках (например, апгрейд версии в
нескольких местах) — таблица: «файл / было / стало».

Diff (- / +) остаётся допустим только для .gitlab-ci.yml,
.md и конфигов, если пользователь явно попросит.

**Вложенные markdown-блоки — обёртка `~~~` (приоритет), 4 backticks (fallback).**

Если правка содержит markdown-разметку — заголовки `###`,
жирный `**`, горизонтальные линии `---`, code-блоки в тройных
backticks — ассистент оборачивает текст правки во **внешний блок
с тильдами** (`~~~`). Внутри — любые backticks, любой длины,
без подсчёта.

**Механизм:**

- Внешняя обёртка — `~~~` с **языковым тегом** (как обычные code-блоки): `~~~python`, `~~~bash`, `~~~markdown`. Закрывается тоже `~~~`.
  Внутри могут быть любые backticks. Проверено в чате:
  отрендеривается как один code-блок, содержимое сохраняется
  дословно, внутренние тройные backticks видны как есть.
- **Fallback:** если `~~~` недоступны (парсер чата не поддерживает
  tilde-fence) — внешний блок из **минимум 4 backticks**. Не
  «макс+1», а «минимум 4»: проще запомнить и выполнить.
- Обычные code-блоки без внутренних backticks — стандартные
  3 backticks, ничего не меняется.

**Типичные случаи:**

- Внутри только одиночные inline-backticks → `~~~` (приоритет)
  или 3 backticks (тоже работает).
- Внутри есть тройные backticks (code-блоки) → `~~~`.
  Fallback — 4 backticks.
- Внутри есть тильды-обёртки (правка этого правила) →
  внешний 4 backticks, потому что `~~~` внутри `~~~` сломается
  так же, как backticks внутри backticks.

**Зачем:** ассистент не видит отрендеренный ответ. Без корректной
внешней обёртки markdown-разметка превращается в заголовки/жирный/
линии прямо в чате, и пользователь не может скопировать raw-текст
для вставки в файл. `~~~` не конфликтует с backticks вообще;
fallback «4 backticks» снимает проблему, если `~~~` не поддержан.

**Проверка перед отправкой (обязательно).** Перед отправкой
code-блока в ответе — механически посмотреть на содержимое:
есть ли внутри 3+ backticks подряд? Если да — обернуть в `~~~`
или в 4+ backticks. Не «на глаз», а явно.

**Запрещено** (в fallback-режиме) использовать обёртку той же
длины, что и максимальная вложенная — она сломается на первом же
внутреннем backtick такой же длины.

**Правило действует для:** правок `.md`-файлов, примеров markdown
в ответах, любых фрагментов, где разметка должна сохраниться
дословно.

**Действие правила для кода.** Правило распространяется не только
на «правки .md», но и на любой код (python, shell, любой heredoc
или triple-quoted string), который содержит markdown как
строковую константу. Если такой код обёрнут во внешний блок и
внутри есть 3+ backticks — внешняя обёртка `~~~` или 4+ backticks.

**Не путать с обычными code-блоками.** Правки `.kt`, `.kts`,
`.yml` не содержат тройных backticks внутри — им хватает
стандартной обёртки из 3.

### 4b. Один шаг за раз

При работе над задачей ассистент выдаёт **одну подзадачу
(шаг) за раз** и **останавливается**. Следующий шаг — только
после явного «дальше» / «ок» / «продолжай» от пользователя.

**Запрещено:**

- Выдавать простыню «шаг 1 → шаг 2 → … → шаг N» в одном
  ответе, даже если все шаги очевидны.
- Начинать следующий шаг самостоятельно, без подтверждения.
- Прятать в конце ответа формулировки «а затем сделай …»,
  «после этого …», «дальше идём на …» — это неявный толчок
  вперёд, эквивалентный выдаче нескольких шагов.

**Формат ответа на каждом шаге:**

1. Что делаем сейчас — одно предложение.
2. Правки в формате «было → стало» (см. 4a).
3. Команды для проверки (сборка / тесты / что угодно).
4. Одна строка: «Останавливаюсь. Жду результата / „дальше“».

**Исключение:** пользователь явно просит полный план
(например, «распиши все шаги», «составь план»). Тогда
ассистент выдаёт план целиком — но как **план**,
без выполнения. Выполнение всё равно идёт по шагам.

**Исключения из «одного шага за раз»** — сценарии, где
формат ответа задан отдельным правилом и переопределяет
4b:

- **5b** — правка `docs/` + готовый commit message в
  одном ответе (атомарная пара).
- **5f** — post-PR чек-лист (одним блоком, одна
  остановка после последней команды).
- **4c** — механическая правка скриптом (команда
  выдаётся целиком, без дробления на подшаги).

В этих случаях действует формат из соответствующего
правила, а не дробление по шагам. При сомнении между
общим (4b) и частным — применяется частное.

**Разделение понятий:**

- **План** (в `docs/ROADMAP.md` или по явному запросу) —
  все шаги сразу, самодостаточно (см. 5e).
- **Ведение по задаче** (в чате, при реализации) — по одному
  шагу, с остановкой после каждого.

Эти два режима не смешиваются.

**Причина:** пользователь должен успеть проверить результат
шага и решить, продолжать ли. Особенно на телефоне, где
каждая правка требует внимательного прочтения, а автофикс
или массовый рефакторинг может задеть неожиданные места.

**Находки вне scope.** Если при чтении кода для задачи
обнаружена ловушка вне scope (баг, потенциальная гонка, утечка,
некорректная обработка ошибки) — ассистент не игнорирует её молча.

- **Мелкая и очевидная** (одна строка, ясная причина) —
  упомянуть в ответе одной строкой, без отдельного шага.
- **Требует разбора** — предложить записать в `docs/ISSUES.md`
  отдельным шагом (по 4b), с оценкой серьёзности.

**Не путать с аудитом.** Правило не обязывает искать ловушки
при каждой задаче — только не терять те, что попались при
чтении кода по делу.

**Причина:** в сессии 2026-10-18/19 ловушки (replay-leak,
бесконечный retry на `UNAUTHENTICATED`, утечка WS-сессии) были
найдены только потому, что пользователь явно попросил
«поищем». Без запроса ассистент мог их молча пройти мимо —
а они были критичны для диагностики WS.

### 4c. Механические правки — скриптом

Если правка описывается **механически** — «заменить X на Y»,
«удалить блок между маркерами», «вставить перед строкой Z»,
«массовая замена по всем файлам» — ассистент **обязан**
давать готовую команду (`sed`, `python3` через heredoc,
`awk`), а не текст «найди и вставь руками».

**Когда команда:**

- Замена по маркеру: `### Заголовок` → `### Новый заголовок`.
- Удаление секции по границам (от `### X` до `---` перед
  следующим `### Y`).
- Вставка блока в определённое место.
- Массовые однотипные замены.
- Схлопывание дублирующихся пустых строк / `---` / пробелов.

**Когда только текст:**

- Пользователь явно попросил «пришли текст, я сам поправлю».
- Правка интерактивная — решения принимаются по ходу.
- Много мелких вставок в разных местах, где скрипт окажется
  длиннее текста.

**Общий принцип:** если правка механически описывается —
команда. Если это вставка новой секции целиком — тоже
команда (heredoc + append или вставка по маркеру).

**Правки в `.md` и конфигах — всегда скриптом.** Формат
«было → стало» (4a) показывается для чтения, но
применение — только через скрипт. Исключение — когда
пользователь явно просит «пришли текст, я сам поправлю».
Причина: ручное копирование многострочных блоков через
экран телефона — источник опечаток; скрипт с assert'ами
ловит рассинхронизацию до записи.

**Зачем:** команда не оставляет места для ошибок «не туда
вставил», «не то удалил», «потерял строку при копировании».
Особенно важно для больших `.md`-файлов, где ручное
редактирование через экран телефона — источник опечаток.

**Примеры формата:**

Удаление секции по маркерам:

    python3 <<'PYEOF'
    from pathlib import Path
    p = Path("docs/ROADMAP.md")
    lines = p.read_text(encoding="utf-8").splitlines(keepends=True)
    start = next(i for i, l in enumerate(lines)
                 if l.startswith("### Каскад обновления позиций"))
    end = next(i for i, l in enumerate(lines) if i > start
               and l.startswith("### Переход на edge-to-edge"))
    p.write_text("".join(lines[:start] + lines[end:]),
                 encoding="utf-8")
    PYEOF

Вставка секции перед маркером:

    python3 <<'PYEOF'
    from pathlib import Path
    p = Path("docs/ROADMAP.md")
    text = p.read_text(encoding="utf-8")
    marker = "### Рефакторинг расчёта P&L"
    new_block = """### Новая задача

    **Статус:** запланировано.
    ...
    """
    p.write_text(text.replace(marker, new_block + marker, 1),
                 encoding="utf-8")
    PYEOF

**Скрипт и его верификация — в одном блоке.** Скрипт
правки (`python3` heredoc, `sed`, `git mv`, `git commit`) и
verification-команды, которые проверяют результат (`grep`,
`git diff --stat`, `wc -l`, `git log`), выдаются в **одном**
shell-блоке. Пользователь запускает блок один раз, видит и
результат применения, и результат проверки — без
дополнительного раунда «пришли вывод скрипта → получи
верификацию».

Причина: два отдельных блока = два round-trip'а;
пользователь ждёт ответ ассистента между ними, а ассистент
тратит ответ на «пришли вывод» вместо движения вперёд. В
proot/мобильном окружении это особенно заметно.

**Исключение:** если вывод верификации нужен, чтобы
**выбрать** следующий шаг (например, `git diff` для выбора
между двумя вариантами правок), он остаётся отдельным
шагом по 4b. Скрипт + проверка «применилось / не
применилось» — всегда вместе.

**Не путать с 4a.** 4a — про то, как показывать текст
правки пользователю в чате. 4c — про то, каким способом
вносить правку в файл: командой или вручную.

### 4d. Идемпотентность операций

Операции, которые ассистент предлагает для исполнения
(скрипты для правок файлов, `git mv`, `git remote remove`,
создание тегов, удаление секций), должны быть
**идемпотентными** или **явно проверять предусловие**.

**Зачем:** пользователь не всегда уверен, что операция
применилась. Повторный запуск не должен дублировать
код, портить файл или молча ничего не делать — он должен
либо дать тот же результат, либо явно упасть с сообщением
"уже применено" / "не найдено".

**Три паттерна для скриптов правок:**

**Паттерн 1 — assert на маркер отсутствия.**

Перед вставкой нового блока:

    assert "@Preview" not in text, "Превью уже добавлены"

Если маркер уже есть — скрипт упадёт, а не вставит
дубликат.

**Паттерн 2 — assert на существование + замена с count=1.**

Перед заменой фрагмента:

    assert old_fragment in text, "Заменяемый фрагмент не найден"
    text = text.replace(old_fragment, new_fragment, 1)

Если фрагмент уже заменён — assert не пройдёт, потому
что old_fragment в файле больше нет.

**Оговорка:** это верно только если `new_fragment` не
содержит `old_fragment` как подстроку. Если содержит
(типичный случай — расширение правила, где новая версия
= старая + дополнение), проверка `old_fragment` после
замены всё равно пройдёт, и второй запуск скрипта
вставит блок ещё раз.

**Паттерн 2b — «новая версия расширяет старую».**

Если `new_fragment` содержит `old_fragment` (новая
версия — надмножество старой), порядок проверок
обратный: сначала `if new in text`, потом `if old
in text`.

    if new_fragment in text:
        print("already applied")
        return
    assert old_fragment in text, "old not found"
    text = text.replace(old_fragment, new_fragment, 1)

После записи проверять **count** нового фрагмента:

    assert final.count(new_fragment) == 1, \
        "apply produced != 1 copies"

Не `assert old not in text` — при new = old + suffix
этот assert не может пройти никогда.

**Паттерн 3 — проверка после записи.**

    p.write_text(text, encoding="utf-8")
    assert new_marker in p.read_text(encoding="utf-8"), \
        "Правка не применилась"

Проверяет, что запись действительно произошла.

**Запрещено в скриптах правок:**

- Append без проверки (`text += new_block` в цикле
  повторов).
- `replace(...)` без `count=1`, если шаблон может
  встретиться несколько раз.
- Молчаливый `try/except` вокруг записи — пользователь
  должен узнать об ошибке.
- Использовать `assert` только как «отладку» без
  сообщения. Сообщение в assert — часть UX: оно
  подсказывает, что пошло не так.

**Для операций с git:**

- `git branch -d <name>` — сам по себе безопасен,
  упадёт если ветка не смержена.
- `git remote remove <name>` — идемпотентен не сам
  по себе, но перед ним ассистент проверяет
  `git remote -v` и при отсутствии говорит
  «remote уже удалён».
- `git push origin --delete <branch>` — падает с
  ошибкой, если ветка уже удалена; ассистент
  проверяет `git ls-remote --heads origin <name>`
  перед командой.

**Правило действует для всех операций, которые
предлагает ассистент.** Если идемпотентность
недостижима (например, «удалить последний коммит»),
ассистент явно предупреждает: «операция не
идемпотентна, выполняй один раз».

**Trailing whitespace в markdown.** Скрипты вставки в
`.md`-файлы **не создают trailing spaces**. Шаблон в heredoc
не содержит отступов после последнего непробельного символа
строки. Если правка идёт многострочным блоком — прогнать
каждую строку через `rstrip()` перед записью:

    text = "\\n".join(line.rstrip() for line in block.splitlines())

Причина: trailing spaces ломают `assert` с точным сравнением
строк, дают шум в `git diff`, потенциально — ошибки
markdown-линтеров.

Проверка после записи:

    assert new_block.rstrip() == new_block, \\
        "trailing whitespace в новом блоке"

**Проверочный маркер должен появляться именно после
правки.** Если в `assert ... in text` используется строка,
которая никогда не будет в файле (даже после успешной
записи), — проверка бесполезна: пропускает и ложно-
положительный, и ложно-отрицательный результат.

**Проверочный маркер должен быть уникален в файле.**
`assert count(new_marker) == 1` падает с ложным негативом,
если `new_marker` встречается в файле больше одного раза
— например, в комментарии и в коде, или в самом
добавляемом блоке (шаблон + пояснение).

Порядок проверки:

1. Сначала `if new_marker in text: print("already applied")`.
2. Затем `assert old_marker in text`.
3. После записи — `assert count(new_marker) == N`, где
   `N` — **ожидаемое** число вхождений (может быть
   больше 1, если маркер намеренно встречается в
   нескольких местах). Не хардкодить `1` «по привычке».

Практический приём: выбирать маркер с уникальным
окружением (отступ + символы вокруг), а не голую фразу.
Пример: `'val subscriptions: SubscriptionsDto?'` вместо
`'SubscriptionsDto'`; `'            encodeDefaults = true'`
с отступом вместо `'encodeDefaults = true'`.

Если правка добавляет фразу, которая **внутри блока
встречается несколько раз** (комментарий + код + абзац
пояснения) — `count == 1` не подходит. Тогда либо
проверять уникальный фрагмент (`'            encodeDefaults = true'`),
либо использовать `count(new_marker) >= expected_count`.

**Проверка «старой формы больше нет» — только если новая
форма её не содержит.** Паттерн «переименование» или
«замена формы» часто пишется так:

    assert new_form in text
    assert old_form not in text

Это ломается, если `new_form` **намеренно** содержит
`old_form` как подстроку. Типичный пример — правило о
ветках `docs/<topic>`: новая формулировка говорит
«Ветки `docs/<topic>` не используются», то есть содержит
запрещённую строку, и `assert old_form not in text` падает
с ложным негативом.

Правильно — проверять **семантическую замену**, а не
отсутствие подстроки:

- либо `assert old_form not in text` применим только к
  короткой форме, которая в новом тексте не встречается
  в **рабочем** контексте (например, `old_form` — точная
  строка в коде, а новая формулировка — это комментарий);
- либо проверять `count(old_form) == expected_old_count`,
  где `expected_old_count` — сколько раз старая форма
  должна остаться (обычно 0, но в некоторых правках — N);
- либо использовать `assert text.count(new_form) == 1`
  и **не проверять** отсутствие `old_form` вообще —
  достаточно того, что новая форма встала на место.

**Не писать `assert old_form not in text` по привычке.**
Если есть хоть малейший риск, что новая формулировка
содержит старую как подстроку, — этот assert запрещён.
Проверять либо `count(new_form) == expected`, либо
конкретную уникальную подстроку.

**Инцидент-счётчик.** За сессию 2026-10-20 три ложных
негатива на этой почве:
1. `encodeDefaults = true` — маркер встречался в комментарии
   и коде, `count == 1` упал.
2. `git add <files>` — маркер встречался в трёх местах
   добавленного блока, `count == 1` упал.
3. `docs/<topic>` — новая формулировка намеренно содержит
   старую строку, `not in text` упал.
Все три — не ошибки применения, а ошибки проверки. Правило
введено, чтобы четвёртого не было.

**Проверка «старой формы больше нет» — `grep` в shell после
записи, не Python `assert`.** `assert "old" not in
text.replace(new, "")` даёт ложные срабатывания, когда `old`
встречается как часть других идентификаторов: `repository.`
внутри `data.repository.SettingsRepository`, `getAccounts`
внутри `getAccountsResult`. Такой assert падает **до**
`p.write_text` — скрипт не применяется, но пользователь
видит ошибку и не знает, что она ложная. Правильно —
записать файл, затем `grep -nE '(^|[^A-Za-z_.])old'` в том
же shell-блоке (граница: голый `old` после не-буквы и
не-точки, не внутри `xxx.old`).

Пример (2026-10-27, миграция `SettingsViewModel`):
`assert "repository." not in text` упал на импорте
`data.repository.SettingsRepository` — `repository.` как
подстрока есть в пути пакета, хотя голых `repository.` в
коде уже не было. Ложный assert остановил скрипт до записи.
Правильная проверка —
`grep -nE '(^|[^A-Za-z_.])repository\.'` (голый
`repository.` после пробела / скобки / начала строки, не
после точки).

Правильный маркер — уникальная подстрока из вставляемого
блока (например, имя первой новой функции, уникальное
имя поля, отпечаток новой секции). Не из общих слов.

**Пример ошибки:** вставляется функция
`BrokerAccountDialogTInvestPreview`, а проверяется
наличие `BrokerAccountDialogPreview` — подстрока
не совпадает, проверка проходит вхолостую.

**Правильно:** проверять `BrokerAccountDialogTInvestPreview`
или `@Preview(name = "T-Invest — with accounts"`.

**Правило может быть описано в нескольких местах.**
Перед правкой правила — `grep` по ключевым фразам
всех его блоков во всех `.md` проекта:

    grep -n "Чек-лист post-PR\|Формат ответа ассистента" AGENTS.md

Пример: 5f состоит из двух блоков — процедуры
(«**Чек-лист post-PR:**») и примера формата
(«**Формат ответа...**»). Правка одного оставляет
второе устаревшим, документ противоречит сам себе.

**`git diff` — часть того же шага.** Показ диффа после
скрипта правки — диагностика, а не действие: read-only,
ничего не меняет. Скрипт и `git diff` идут в одном блоке
команд (через `;` или следующими строками). Если скрипт
упал на `assert`, `git diff` всё равно выполнится —
пользователь увидит фактическое состояние до следующего
решения.

**Пауза для подтверждения применения скрипта — обязательна.**
После блока «скрипт + верификация + `git diff`» ассистент
**останавливается** и ждёт явного подтверждения
пользователя, что изменения корректны. Скрипт меняет
файл — это точка контроля до того, как на результат будет
построен следующий шаг (коммит, миграция потребителя,
следующий шаг задачи).

Формат:

    Скрипт применён. Проверьте вывод: <ожидаемое состояние>.
    Останавливаюсь. Жду подтверждения применения.

**Деструктивные операции** (`push`, `reset --hard`,
`delete`, `rebase`) — пауза **до** операции (предупреждение
и ожидание «да»), не после. Обычные правки файлов — пауза
**после** (подтверждение применения).

### 4e. Безопасность shell-команд в ответах

**Инцидент-триггер:** сессия 2026-10-20/21. Markdown-блок
с задачей Codecov (заголовки, проза, `~~~yaml`-пример с
`git push --mirror`) был вставлен пользователем в терминал
целиком. Bash выполнил все строки как команды, включая
`git push --mirror` на origin. Последствия: удалены 4
ветки (`ci/self-hosted-runner`, `feature/hilt-koin-inventory`,
два `renovate/*`), созданы мусорные `WIP`, `temp` и
`refs/remotes/*`, `refs/gitlab/*`. Восстановлено вручную,
потерян только `renovate` (бот пересоздаст).

**Правило 1 — разделение «команда» и «пример».**
Markdown-блок с shell-командами для выполнения пользователем
содержит **только** команды. Никакой прозы, заголовков,
YAML-примеров, пояснений. Если нужен пример конфига —
отдельный блок с явным предупреждением в тексте **перед**
блоком: «Пример конфига, не для терминала».

Запрещено: смешивать в одном блоке shell-команды и
YAML/markdown-примеры. Причина — инцидент выше.

**Правило 2 — опасные операции только с `--dry-run`.**
Следующие команды выполняются в два шага: сначала
`--dry-run` (или эквивалент), пользователь видит вывод,
подтверждает, потом выполнение:

- `git push --delete`, `git push --force`, `git push --mirror`;
- `git reset --hard`, `git clean -f*`, `git branch -D`;
- `git remote remove`, `git tag -d`;
- `rm -rf`, `find ... -delete`, `chmod -R`;
- `docker system prune`, `podman system prune`.

В сообщении — явное «это удалит X, Y, Z», потом
`--dry-run`, потом выполнение. **Не** «сразу команда,
потом посмотрим».

**Правило 3 — `git push --mirror` запрещён.**
`--mirror` пушит **все** локальные refs, включая
`refs/remotes/*`, `refs/gitlab/*`, локальные
экспериментальные ветки. На remote это создаёт мусорные
ветки с именами `origin/dev`, `gitlab/master` и т.п.,
а **отсутствующие** на remote ветки — удаляет. Это уже
случилось в инциденте выше.

Для зеркалирования между GitHub и GitLab — только явные
refspec: `git push gitlab refs/heads/*:refs/heads/* refs/tags/*:refs/tags/*`.
Или через `git ls-remote` + точечный push. Никогда
`--mirror`.

**Правило 4 — блок «команды для проверки» отдельно от
блока «объяснение».** Если в ответе есть и объяснение,
и команды — это **разные** markdown-блоки. Пользователь
копирует только блок с командами.

Если `grep` находит несколько вхождений — править все
в одном шаге, а не по частям.

**Секреты — только из файла или переменной окружения.**
В любых командах, которые ассистент выдаёт пользователю
(token, пароль, API-key, private key), значение читается
из файла или переменной окружения, не вставляется
литералом:

    -H="Authorization: Bearer $(cat ~/.keystores/.tinvest_token)"

Запрещено:

- Просить пользователя вставить токен/пароль в чат «чтобы
  я подставил».
- Давать команду с литеральным токеном — даже
  placeholder'ом типа `<TOKEN>`, потому что пользователь
  подставит реальное значение, и оно уйдёт в историю shell.

Причина: история чата, история shell, скроллинг — всё это
носители секретов. Read-only токен — тоже секрет (портфель,
заявки, финансовая информация).

Триггер: сессия 2026-10-21, токен T-Invest вставлен в чат
открытым текстом через websocat-команду.

**Правило 5 — не пайпить Gradle в `grep -q` / `head -1`.**
Команды вроде `if ./gradlew ... | grep -q "FAILED"; then ...`
опасны: `grep -q` закрывает pipe при первом матче, долгоживущий
процесс (Gradle) получает SIGPIPE и может уронить shell. На
proot / ограниченной машине это вырубало терминал дважды
(2026-10-22, задачи SettingsViewModel и Race-тесты).

Безопасно:
- `./gradlew ... 2>&1 | tail -20` — читает до конца.
- `./gradlew ... > /tmp/out.log 2>&1; grep -c PATTERN /tmp/out.log` —
  сначала полный прогон, потом анализ.
- В цикле `for i in 1..N` — **без** `grep -q`, результаты
  копить в файл, разбирать после.

Правило касается любого долгоживущего процесса в pipe: Gradle,
adb logcat, adb shell с длинным выводом, python3 heredoc с
интерактивным вводом.

### 5. Коммит после каждой задачи

Как только задача завершена и проверена (сборка зелёная,
на устройстве работает) — ассистент предлагает коммит с готовым
сообщением в стиле:

`<type>(<scope>): <краткое описание>`

`<тело: что изменилось и почему>`

Типы: `feat`, `fix`, `refactor`, `chore`, `docs`, `test`.

**`wip` — не тип.** Стандартный тип (`feat`, `fix`, ...) ставится
в заголовок всегда, даже для промежуточного WIP-коммита. WIP-статус
и среда (mobile/desktop) — **в теле** первой строкой:

    WIP — <среда>, <гейт>; not final.

Пример:

    feat(domain): add OrdersApi role interface

    WIP — mobile (proot), CI gate; not final.
    - Add domain/api/roles/OrdersApi.kt with 6 methods...

**Язык коммитов — только английский.** Заголовок и тело.
Русский в commit message запрещён, даже если обсуждение задачи
идёт на русском.

**Цитаты — тоже на английском.** Если в коммите нужно
сослаться на русскоязычный текст (название правила,
название задачи, сообщение об ошибке, идентификатор из документации),
цитата переводится или перефразируется на английский.
Дословная русская цитата внутри английского текста
запрещена, даже в кавычках.

Пример:
- Запрещено: `Kept branch-side rules: "Одна правка — один
  блок", "Проверочный маркер должен быть уникален".`
- Правильно: `Kept branch-side rules: "One edit, one block",
  "Verification marker must be unique".`

Единственное исключение: если русскоязычный фрагмент — это
код-идентификатор (имя файла, имя поля в коде, точная строка
из `.kt`-файла), который нельзя перевести без потери смысла.
Тогда он остаётся в backticks как код, а пояснение вокруг —
на английском. Пример: `kept field "blocked" as-is`.

**Правило распространяется на все текстовые артефакты
репозитория:** commit message, тело PR/MR, комментарии
в PR/MR, сообщения тегов, release notes, код-ревью.
Всё, что остаётся в истории и доступно другим —
на английском.

Чат с пользователем — на русском (см. «Коммуникация»).
Граница проходит по репозиторию, а не по теме обсуждения.

Коммит — точка отката. Не коммитить «в конце дня» пачкой.

Исключение: если работа идёт с устройства без доступа к
терминалу (телефон, веб-интерфейс GitLab без локального
репозитория) — допустимо накапливать изменения и закоммитить
одним блоком при первой возможности. Такой блок в commit
message должен быть явно разделён на смысловые части в теле
(разделы `- area: ...`), даже если физически это один коммит.

### 5a. Порядок коммита: локально vs CI

**Локальные изменения** (код, ресурсы, Gradle-конфиги, документация):
коммит **после** зелёного полного гейта (см. ниже).
Если гейт падает — сначала фикс, потом коммит.

**Перед открытием PR — полный гейт.** Минимум
`testDebugUnitTest` недостаточен: CI прогоняет `fast-check`
(unit + lint + ktlint + detekt). Все четыре задачи должны
быть зелёными **до** открытия PR (локально или на CI —
см. «Локальный гейт и CI гейт равнозначны»). Иначе
lint/ktlint/detekt падают на PR — как было в сессиях
2026-10-20/21: ktlint на
`TInvestPositionsWsMapper.toAmountOrZero` и
`TInvestOrderStateWsMapper.toDoubleOrNull`, detekt
MagicNumber в `StreamCombinators`.

**WIP-коммиты в `feature/*` — точка отката, не точка приёмки.**
Гейт на каждом WIP-коммите **не требуется**. Граница гейта —
открытие PR (последний коммит feature-ветки). Post-push
проверка защищённых веток (см. ниже) — отдельный ритуал,
не путать с гейтом на WIP.

Команда:

    ./gradlew :app:clean :app:testDebugUnitTest :app:lintDebug \
      :app:ktlintCheck :app:detekt --rerun-tasks \
      2>&1 | grep -E '\[warn\]|\[error\]|^w:|^e:|FAILED|BUILD'

Ожидаемо: `BUILD SUCCESSFUL`, все гейты зелёные, только
известные warning'и (`statusBarColor`, Gradle 10).

**Локальный гейт и CI гейт равнозначны.** Локальная команда
выше и CI job `gate` (в Rulesets — required check) покрывают
одни и те же четыре задачи: `testDebugUnitTest`, `lintDebug`,
`ktlintCheck`, `detekt`. CI дополнительно запускает
`full-build` (koverVerifyDebug + assembleDebug) — **шире**
локального гейта. Свежий checkout на CI эквивалентен
`clean` локально.

Если CI `gate` на запушенном коммите зелёный — локальный
повтор перед merge **не требуется**. Required check
`gate` технически блокирует merge: PR без зелёного `gate`
не пройдёт, даже если кто-то попытается нажать кнопку.

**Когда CI не заменяет локальный гейт.** Три случая:
1. CI недоступен (нет runner'а, сломана инфраструктура).
2. Задача требует live-теста на устройстве — это только
   локально (см. `docs/live-test.md`).
3. Сработал `paths-ignore` на смешанном коммите (docs + код
   вместе): CI не запустится, но в коммите есть код. В этом
   случае — либо разделить коммиты, либо локальный гейт.

**Оптимизация, не обязательность.** Ошибка стиля или линтера
на PR — это лишний цикл push→CI→fix. Полный локальный
прогон занимает ~50 секунд, дешевле цикла CI. Но если
WIP-коммиты уже запушены и `gate` зелёный — merge разблокирован,
локальный повтор не нужен.

**Исключение: docs-only коммиты.** Если в коммите изменены
**только** `.md` файлы (никаких `.kt`, `.kts`, `.yml`,
`.yaml`, `.xml`, `.gradle`), полный гейт не требуется.
Ни один из четырёх гейтов (testDebugUnitTest, lintDebug,
ktlintCheck, detekt) `.md` не валидирует — прогон 40–50
секунд ради ничего.

Вместо полного гейта для docs-only:

- `git diff` — структурная проверка: что меняется, где,
  нет ли артефактов;
- ручная проверка на типичные ошибки markdown:
  - двойные `---` подряд;
  - незакрытые fence'ы (``` или ~~~);
  - trailing whitespace;
  - битые ссылки на перемещённые/удалённые секции.

Автоматическая проверка `.md` появится отдельной задачей:
`docs/ci-roadmap.md` → «Markdown linter в CI». До тех пор —
ручная проверка по чек-листу выше.

**CI/CD изменения** (`.gitlab-ci.yml`, CI-скрипты, конфиги пайплайна):
коммит **до** проверки. Пайплайн не воспроизводится локально,
поэтому порядок обратный:
1. внести правку;
2. закоммитить;
3. запушить и дождаться результата пайплайна;
4. пайплайн зелёный → следующий шаг;
5. пайплайн красный → фикс **отдельным коммитом** (не `--amend`,
   не force-push в `master`/`dev`).

**Смешанные изменения** (код + CI в одной задаче) — **два коммита**,
по одному на область. Не смешивать.

**Общий принцип:** один коммит — одна задача. Дробление на этапы
приветствуется, лишь бы каждый коммит был логически завершён и
точка отката была осмысленной.

**Post-push проверка защищённых веток.** После `git push`
в `dev`, `master`, `release/**`, `hotfix/**` —
два обязательных шага:

1. **Проверить, что коммит в origin:**
   `git log --oneline -3 origin/<branch>` + `git status`.
   Ожидаемо: коммит виден, ветка не расходится с origin.
2. **Дождаться зелёного CI** на запушенном коммите.
   Следующий шаг не начинается до результата.

Причина: rulesets не воспроизводятся локально. Push
может пройти, но CI упадёт — и это обнаружится только
на PR следующей задачи, где уже неочевидно, чей это
красный.

Если CI красный — фикс **отдельным коммитом** (не
`--amend`, не force-push).

### 5b. Правки в docs — сразу с коммитом

Любая правка в `docs/` или `AGENTS.md` сопровождается готовым
сообщением для коммита в том же ответе ассистента. Не отдельным шагом «скажи, когда
закоммитишь», не «пришлю сообщение позже».

Формат ответа для каждого документа — **один блок**:

1. Файл, было/стало.
2. Готовый commit message — **одной командой**, готовой
   к вставке в терминал (см. ниже).
3. Одна строка — что делать дальше.

**Commit message — только скриптом.** Правки `.md`/`.yml`/
`.kt`/`.kts` — через скрипт (4c). Commit message — тоже
текст, который пользователь вставляет в терминал. Голый
текст в чате для копирования через экран телефона —
запрещён, по той же причине, что и ручной копипаст
markdown: опечатки, переносы, потеря строк.

Формат — heredoc через `git commit -F -`:

    git add <files>
    git commit -F - <<'MSGEOF'
    <type>(<scope>): <краткое описание>

    <тело: что изменилось и почему>
    MSGEOF

`git add <files>` — обязательный первый шаг, файлы
перечисляются явно. `git add .` / `git add -A` /
`git add -u` — запрещены: подхватывают лишнее из
рабочего дерева.

Одна команда, копируется целиком, вставляется в терминал
как есть. Тот же приём — для `git tag -a` (через `-F -`)
и для `git commit --amend` (если правка исправляет
незапушенный коммит).

Heredoc-обёртка — обязательна для всех коммитов, в том
числе когда тело короткое. Визуально удобно: граница
MSGEOF отделяет сообщение от следующих команд, копируется
без захвата лишнего.

Если правится несколько документов (`AGENTS.md` +
`docs/ROADMAP.md`, `docs/ROADMAP.md` + `docs/ISSUES.md`
и т.п.) — **отдельный блок
на каждый документ**, каждый со своим commit message.
Это разные задачи, коммиты не смешиваются.

Запрещено выносить commit message в отдельный блок
ответа — «сначала все правки, потом все коммиты».
Правка и её коммит — атомарная пара.

Правило действует для всех документов проекта.

### 5c. Структура ответа

Ответ собирается из стандартных блоков. Применяются
по необходимости — не раздувать.

1. **Диагностика.** Что проверено, что видно, чего не видно.
2. **Варианты.** Если 2+ разумных решения — перечислить
   с плюсами и минусами.
3. **Рекомендация.** Какой вариант и почему.
4. **Правки.** Формат «было → стало» (см. 4a).
5. **Коммит-сообщение.** Готовый текст (см. 5b).
6. **Порядок.** Что делать сейчас, что потом.

Пустые блоки опускаются. Тривиальная задача (одна строка,
опечатка) — только 4 и 5.

### 5d. Жизненный цикл задачи

Для задач, зафиксированных в ROADMAP, применяется
трёхфазный цикл.

**Фаза 1 — открытие.**

Ответ содержит блоки 1–3 (диагностика, варианты,
рекомендация). Ассистент **ждёт утверждения** от
пользователя. Только после «да» — коммит:

    docs(roadmap): plan <название>

В теле: что планируется, зачем, варианты, выбранный подход,
оценка.

**Фаза 2 — реализация.**

Начинается **после** коммита плана. Каждый шаг — блоки 4–6
(правки, коммит, порядок). Между шагами — сборка (п. 4).
Один логически завершённый шаг — один коммит.

**Тесты — часть реализации.**

Если задача добавляет или меняет код с проверяемыми
инвариантами (мапперы, fallback-логика, обработка ошибок,
бизнес-правила) — тесты пишутся в **той же** feature-ветке.
Обычно — последним коммитом Фазы 2, после стабилизации кода.
При TDD или когда тест пишется для каждого метода — возможно
вместе с кодом. Ключевое: тест в ветке **до** `mark done`,
не в отдельном PR после merge.

Порядок для «код + тесты вместе»:
1. Фаза 2: код, зелёный гейт.
2. Фаза 2: тесты на новую логику, зелёный гейт.
3. Фаза 3: `mark done`.

**Почему не отдельным PR:** двойной gate, двойной review,
двойной merge. При соло-разработке — overhead без пользы.
Отдельный PR «только тесты» оправдан лишь когда тесты
дописываются к уже смерженному коду — тогда это **отдельная
задача** в ROADMAP с обоснованием, а не хвост текущей.

**Отложенные тесты фиксируются явно.** Если тест невозможно
написать сейчас (нужна mock-инфраструктура, нужен рефакторинг,
JVM-тест невозможен без Robolectric) — это **не «забыли»**,
а осознанное решение:
- в теле `mark done` коммита — явная фраза «покрытие тестами
  отложено: <причина>»;
- отдельной задачей в ROADMAP — с критерием готовности.

Молча не откладываются.

**Проверка затронутых файлов.**

При написании тестов — пройтись по *затронутым* файлам,
а не только по изменённым строкам. Если в файле есть
публичная функция/класс, которые не тестировались до задачи,
но теперь участвуют в новом потоке данных (вызываются из
нового кода, зависят от него, разделяют с ним инварианты) —
оценить, нужен ли им тест.

**Критерий «добавлять или записывать»:**
- **Тривиальный тест** (5–10 минут, чистая функция, нет
  mock-инфраструктуры) и напрямую проверяет новый инвариант
  — добавить в текущий PR.
- **Отдельная сущность** (нужна mock-инфраструктура, >10 минут,
  свой класс/модуль) — записать в `docs/ISSUES.md` как
  отдельную задачу. Не раздувать PR текущей задачи.

Цель: не пропустить «соседний» пробел, но и не смешивать
в одном PR несколько задач.

**Фаза 3 — закрытие.**

Финальный коммит по коду (если ещё не сделан). Затем коммит
в ROADMAP:

    docs(roadmap): mark <название> done

Секция переносится в раздел «Закрытые задачи» в формате
`### ✅ <Название>` с кратким описанием результата.

Отменённые задачи:

    docs(roadmap): mark <название> cancelled

Причина — в теле коммита.

**Тривиальные задачи** (одна строка, опечатка, правка
параметра) — цикл не применяется. Один коммит.

**Пример:**

1. Ответ: диагностика + варианты A/B + рекомендация A.
2. Пользователь: «A».
3. Коммит `docs(roadmap): plan <задача>`.
4. Ответ: правки «было → стало», коммит `chore(...): ...`.
5. Ответ: правки, коммит.
6. Коммит `docs(roadmap): mark <задача> done`.

### 5e. Самодостаточность планов

Любой план, зафиксированный в `docs/ROADMAP.md`,
`docs/ISSUES.md` или в коммите типа
`docs(roadmap): plan ...`, должен быть
**самодостаточным**: другой ассистент (человек или агент)
без доступа к истории чата обязан уметь его реализовать
по одному только описанию.

**Обязательные поля записи:**

- **Статус:** запланировано / в работе / отложено.
- **Контекст:** зачем задача, какую проблему решает.
- **Соответствие Clean:** соответствует | отклонение по 2c
  (принято) | отклонение (открыто). Обязательно для каждой
  задачи, независимо от источника (clean-audit или нет).
- **Нарушенное правило Clean:** одна строка. Для
  «соответствует» — «—».
- **Clean-альтернатива:** как правильно, с плюсами и
  минусами. Для «соответствует» — «—».
- **Выгоды (для «отклонение по 2c»):** что даёт текущий
  вариант — конкретно. Для остальных статусов — «—».
- **Предусловия:** что должно быть сделано до начала
  (какие задачи, какие обновления SDK, какие санкции).
- **Файлы:** конкретные пути и классы, которые будут
  затронуты. Если файл ещё не создан — указать, где
  его создать.
- **Шаги:** пронумерованная последовательность действий.
  Один шаг — одно логически завершённое изменение.
- **Референсы:** ссылки на SDK, официальную документацию,
  примеры в репозитории, related-файлы в самом проекте.
- **Ограничения:** что нельзя делать, известные грабли,
  антипаттерны, которых избегаем.
- **Критерий готовности:** как проверить, что задача
  выполнена (какое поведение должно наблюдаться,
  какие тесты должны проходить).
- **Оценка:** время в часах или минутах.
- **Зависимости:** какие задачи блокируют эту,
  какие блокируются этой.
- **Открытые вопросы:** факты, которых не хватает
  для реализации (имя метода, формат сообщения,
  состав полей proto). Каждый — с указанием, где
  искать ответ.

**Clean-поля обязательны для каждой задачи.** Незаполненное
Clean-поле — сигнал сделать проверку на соответствие Clean и
заполнить. Правило действует для задач в `docs/ROADMAP.md` и
`docs/ci-roadmap.md`. Для записей в `docs/ISSUES.md` Clean-поля
не требуются — проблемы описывают симптом, а не план
реализации (Clean-проверка для них не применима).

**Запрещено в описании плана:**

- Ссылаться на «как обсуждали в чате», «см. выше»,
  «тот же подход, что для задачи X».
- Оставлять шаг без указания файла, в котором он
  делается.
- Указывать в «Референсах» URL без пояснения, что
  именно там смотреть.
- Формулировать шаги в стиле «доработать каскад» без
  конкретики — что именно и где.

**Правило действует для всех документов проекта.**

### 5f. Post-PR checklist

После сообщения пользователя «PR смержен» / «MR смержен» /
«merged» ассистент **обязан**:

1. **Остановиться.** Не переходить к следующей задаче,
   не предлагать «следующий шаг».
2. **Выдать чек-лист post-PR** (см. ниже) и ждать
   подтверждения пользователя по каждому пункту.
3. Только после выполнения чек-листа — переходить к
   следующей задаче.

**Чек-лист post-PR (выполняется одним блоком):**

```bash
# 1. Спрятать локальные правки (если есть)
git stash 2>/dev/null || echo "nothing to stash"

# 2. Переключиться и синхронизироваться
git checkout dev
git remote update
git merge --ff-only origin/dev

# 3. Вернуть правки обратно
git stash pop 2>/dev/null || echo "nothing to pop"

# 4. Удалить локальную ветку (если не смержена, упадёт)
git branch -d <branch>

# 5. Удалить удалённую ветку (если уже удалена, пропустит)
git push origin --delete <branch> 2>/dev/null || echo "skip: remote already gone"

# 6. Пауза для синхронизации GitHub backend (иначе branch -r может показать старую ссылку)
sleep 2

# 7. Проверить, что ветки нет
git branch -r | grep <branch> && echo "STILL EXISTS (check manually!)" || echo "remote branch deleted"

# 8. Проверить рабочее дерево
git status
```

Если `grep` в шаге 7 нашел ветку (несмотря на `sleep 2` и успешный push --delete), это скорее всего кэш локального репозитория. Выполнить `git remote prune origin` и проверить `git branch -r` еще раз.

9. Если задача из `docs/ROADMAP.md` — **проверить**, что
   после merge она в правильном состоянии:
    - **обычная задача**: в `## Закрытые задачи`, заголовок
      `### ✅ <название>`, поля `**Ветка:**` нет
      (mark done сделан в feature-ветке по 5g п.4);
    - **задача с пост-релизным подтверждением**: в
      `## Планируемые задачи`, `**Статус:** в работе`,
      есть строка `**Подтверждение:** <причина, deadline,
      критерий>` (см. 5g п.4, исключение для deferred
      closure).
10. Если ни того, ни другого — это забытый mark done:
   **исправить сразу в `dev`**, отдельным коммитом
   `docs(roadmap): mark <task> done`. Не откладывать
   на следующую сессию.

**Формат ответа ассистента после «PR смержен»:**

    PR смержен. Выполняем post-PR чек-лист:

    1. `git checkout dev`
    2. `git remote update && git merge --ff-only origin/dev`
    3. Удалить локальную ветку: `git branch -d <branch>`
    4. Удалить удалённую: `git push origin --delete <branch>`
       (или проверь `git branch -r`, если GitHub удалил автоматом)
    5. `git status`
    6. Проверить ROADMAP: задача в `## Закрытые` (обычная)
       или в `## Планируемые` с `**Подтверждение:**`
       (deferred closure). Если ни того, ни другого —
       mark done сразу, в `dev`.

    Останавливаюсь. Жду вывода команд.

    Это исключение из 4b: чек-лист выдаётся одним блоком,
    остановка одна — после последней команды. Полный список
    исключений — в 4b.

**Запрещено:**

- Пропускать post-PR чек-лист «потому что очевидно».
- Объединять его с началом следующей задачи.
- Выдавать «следующий шаг» до выполнения чек-листа.

**Причина:** post-PR гигиена — не часть продуктивной
работы, а обязательный ритуал синхронизации. Без
формального чек-листа шаги выпадают из внимания
и накапливаются расхождения между локальной и
удалённой историей.

### Ожидание merge: заморозка feature-ветки

С момента создания PR и до его merge — feature-ветка
**заморожена**. Новые коммиты в неё запрещены (даже doc-only,
даже мелкие фиксы).

**Почему:** если ветка меняется после открытия PR, а в
Rulesets включена опция «Require branches to be up to date
before merging», GitHub пересчитывает merge-статус и
перезапускает CI. Это тратит минуты и ломает поток.

**Что можно во время ожидания:**
- Обсуждать задачу, планировать, читать код.
- Делать правки **прямо в `dev`**, но **без коммитов** —
  оставлять в рабочем дереве (unstaged/staged).

**Post-PR чек-лист (5f) учитывает это:** первый шаг —
`git stash` (спрятать правки), потом `git checkout dev` и
`git merge --ff-only`, затем `git stash pop` (вернуть правки
и закоммитить их обычным порядком).

### 5g. Работа с задачами в ROADMAP

**Куда коммитить документацию.** Документация проекта
делится на три категории по связи с задачей. Порядок
коммита — по правилу 5b (правка + готовое сообщение в
одном ответе).

1. **Связанная с feature/bugfix** — KDoc новой функции,
   изменения в справочниках, если фича их затрагивает.
   Куда: feature-ветка, коммит `docs(<scope>): <описание>`.

2. **Не связанная ни с одной задачей** — правка
   документации вне контекста задачи: справочники,
   структурные изменения, планирование.
   Куда: прямой push в `dev` (см. «Глобальная
   документация — прямой push в `dev`» ниже).

3. **Срочное мелкое** — фикс опечатки, правка заголовка.
   Куда: bypass для Repository admin, прямой push в `dev`.
   Если появится второй разработчик без bypass — правило
   пересматривается.

**Глобальная документация — прямой push в `dev`.**
К `dev` напрямую (bypass Repository admin) идут
документы вне контекста конкретной задачи:

- `AGENTS.md` — директивы ассистента;
- `README.md` — обзор проекта;
- `docs/ROADMAP.md`, `docs/ci-roadmap.md` — планы;
- `docs/ISSUES.md` — известные проблемы;
- справочники `docs/*.md` — streams, brokers,
  release-process, repo-protection, git-flow и т.п.

Ветки `docs/<topic>` не используются.

Почему:

- **Единая область видимости.** Документация — общая
  картина для всех. Ветка `docs/<topic>` прячет правку
  до merge, остальные видят устаревшую версию.
- **Нет ревьюера.** Второй разработчик не знает
  контекста принятых решений, PR-цикл — задержка без
  пользы.
- **Для `AGENTS.md` — срочность.** Правило, найденное
  в сессии, должно применяться сразу, а не после merge.

При появлении второго разработчика, работающего с
ассистентом, — пересмотреть: возможно, для отдельных
типов документов понадобится review.

**Особый случай: `docs/ROADMAP.md` и `docs/ci-roadmap.md`.**

Планы — глобальная сущность. Плановые правки (новая идея,
перестановка приоритетов, пересмотр формулировки) — это
категория 2. Feature-ветки их не таскают.

**Исключение — метаданные о ходе работы над задачей.** Старт
и завершение задачи — часть самой задачи, идут в feature
(см. жизненный цикл ниже).

**Структура файлов:**

- `## Планируемые задачи` — открытые. Свежие сверху.
- `## Закрытые задачи` — принятые. Свежие снизу.

**Жизненный цикл задачи:**

1. **Создание** (руководитель). Задача добавляется в
   `## Планируемые задачи`, статус «запланировано», поле
   «Мобильная работа» заполнено. Коммит в `dev`:
   `docs(roadmap): plan <task>`.

2. **Старт** (исполнитель). Коммит в `dev`:
   `docs(roadmap): start <task>`. Поле «Статус» меняется
   на «в работе», добавляется строка `**Ветка:** feature/<name>`.

3. **Работа** (исполнитель). Feature-ветка создаётся от
   `dev`. Коммиты по коду — обычные, ROADMAP не трогается.

4. **Завершение** (исполнитель). Финальный коммит в
   feature-ветке: `docs(roadmap): mark <task> done`.
   Секция переносится из `## Планируемые задачи` в
   `## Закрытые задачи`, заголовок меняется на
   `### ✅ <название>`.

   **Схема полей при переносе в «Закрытые»:**

   - `**Ветка:**` — **удаляется** (задача смержена).
   - `**Статус:**` — **удаляется** (в закрытой задаче неактуален).
   - `**Подтверждение:**` — **не удаляется**. Переписывается в
     прошедшее время: `**Подтверждение:** выполнено (<дата>,
     <результат>)`. Служит историей — что и когда подтвердили.
   - `**Следующий шаг:**` — **не удаляется**. Переписывается в
     прошедшее время: `**Следующий шаг:** выполнен — <что было>;
     следующий — <актуальный>`. Служит историей навигации.
   - `**Текущее состояние:**` — **переписывается честно**, без
     сокращений: в позитив, если задача закрыта, или удаляется,
     если перекрывается `**Что сделано:**` + `**Подтверждение:**`.
     Сокращать содержимое запрещено (Q-S1 → «не сокращать»).

   **При переносе между блоками содержимое не сокращается.**
   Все блоки секции (`**Контекст:**`, `**Важно:**`,
   `**Предусловия:**`, `**Файлы:**`, `**Шаги:**`, `**Тесты:**`,
   `**Референсы:**`, `**Ограничения:**`, `**Критерий готовности:**`,
   `**Оценка:**`, `**Зависимости:**`, `**Связанные задачи:**`,
   `**Планировали / Сделали:**`, `**Что сделано:**` и т.д.)
   переносятся дословно. Добавлять уточнения — можно.
   Удалять/сокращать — нельзя.

   **Исключение — задачи с пост-релизным подтверждением.**

   **Исключение — задачи с пост-релизным подтверждением.**
   Если результат нельзя проверить до релиза (AppMetrica,
   метрики, live-наблюдение) — mark done в feature-ветке
   **не делается**. Секция остаётся в `## Планируемые
   задачи`, `**Статус:**` меняется на `**Статус:** в работе`,
   и добавляется строка:

       **Подтверждение:** ожидает (<причина>, <deadline>;
       критерий: <как проверять>)

   Пример:

       **Подтверждение:** ожидает (AppMetrica, 2–3 дня
       после релиза; критерий: нет новых fatal
       `io.grpc.StatusException`, появились non-fatal
       `"Unhandled gRPC"`).

   После подтверждения — `docs(roadmap): mark <task> done`
   в `dev` (docs-only), пометка `**Подтверждение:**`
   снимается.

5. **Приёмка** (руководитель). Merge PR = принятие. После
   merge в `dev` задача уже в `## Закрытые задачи`
   (перенос сделан feature-веткой). Отдельного коммита
   после merge **не делается**.

6. **Отклонение** (руководитель). Редкий сценарий. PR
   отклоняется, коммит в `dev`:
   `docs(roadmap): return <task> to work` (или
   `abandon <task>`, если задача отменяется). Задача
   возвращается в `## Планируемые задачи` со статусом
   «в работе» и сохраняет `**Ветка:**`.

**Разделение ролей:**

- **Исполнитель** не ставит статус «принято». Он доводит
  задачу до готовности: финальный коммит переносит её
  в `## Закрытые`. Это декларация «готово к приёмке».
- **Руководитель** подтверждает приёмку фактом merge.
  Если merge не сделан — задача не принята.

**После GitFlow** (см. `docs/ci-roadmap.md` → «Переход на
полный GitFlow») этот регламент переносится в
`docs/git-flow.md` и дополняется спецификой release- и
hotfix-веток.

### Проект

- **Стек:** Kotlin, Jetpack Compose, Hilt, Coroutines/Flow,
  gRPC (T-Invest SDK), REST (BCS, Finam).
- **Слои:** `presentation → domain → data`. ViewModel не ходит
  к брокеру напрямую — только через `InvestRepository`.
- **Структура `domain/`:** новая роль — в `api/roles/`,
  новый менеджер — в `managers/`. Полная структура —
  `docs/architecture.md` (задача `### Архитектурный документ`
  в `docs/ROADMAP.md`).
- **Nullable-val роли.** Паттерн: `val <role>: <RoleApi>?`
  в `BrokerApi`; брокер — `override val <role>: RoleApi get() = this`
  (реализует) или `override val <role>: RoleApi? = null`
  (не поддерживает). **Supertype = «реализую все методы».**
  Если брокер не реализует все методы роли — supertype
  **не ставится**, только `val <role> = null`. Пример #3
  (`b2ef717` → `8ba59f9`): BCS/Finam получили supertype
  `BrokerInstrumentApi`, но не реализуют
  `fetchFullInstrument` — компилятор потребовал
  реализацию. Правильно: `instrument = null` без supertype.
- **Обработка ошибок:** `AppResult<T>` (Success/Failure), не
  исключения на границах слоёв. Ошибки брокеров расшифровываются
  через `BrokerErrorMessages`.
- **Логирование:** `AppLogger`, не `android.util.Log`.
- **Формат логов транспортов:** `<протокол>/<транспорт>/<брокер>`.
  - `[REST/ktor/TInvest] ...`
  - `[WS/ktor/TInvest] ...`
  - `[stream/gRPC/TInvest] ...`
  - `[unary/gRPC/TInvest] ...`
  - `[manager/stream] ...` (менеджер получил данные из любого стрима)
  - `[manager/polling] ...` (менеджер получил данные из любого polling)
- **Цены** — только через `PriceFlowManager`. Не вызывать
  `broker.subscribeLastPrices` и `repository.getLastPricesResult`
  из ViewModel напрямую. Регистрировать интерес через
  `setInterest(PriceConsumer, uids)`.

### Рабочие сценарии: mobile (proot) и desktop (Bluefin)

Проект разрабатывается в двух окружениях. Правила 5/5a
действуют в обоих, но доступные инструменты и порядок работы
различаются.

**Mobile (proot Ubuntu в Termux, телефон).**

- Доступно: терминал, `git`, `grep`, `sed`, `awk`, `python3`,
  правки `.kt` / `.md` / конфигов, `git mv`, коммиты, push,
  PR через web, web UI GitHub/GitLab.
- Недоступно: Android Studio, эмулятор/девайс по ADB, локальный
  запуск Gradle (тяжело для proot, нестабильно), live-тест на
  устройстве (см. `docs/live-test.md`).
- Гейт: **CI `gate` на PR** (см. 5a). Локальный гейт невозможен.
- WIP-коммиты: полное тело (см. 5), первая строка
  `WIP — mobile (proot), CI gate; not final.`
- `type` коммита — стандартный (см. 5), `wip` — не тип.

**Desktop (Bluefin OS, ноутбук/десктоп).**

- Доступно: всё из mobile, плюс локальный Gradle
  (`./gradlew :app:...`), Android Studio, эмулятор/девайс по
  ADB, live-тест на устройстве (`docs/live-test.md`).
- Гейт: **локальный полный гейт** (см. 5a, команда) — быстрее
  CI (~50 сек vs 2–3 мин), не тратит Actions-минуты. CI `gate`
  на PR — подтверждение.
- WIP-коммиты: полное тело (см. 5), первая строка
  `WIP — desktop (Bluefin), local gate; not final.`
  (если коммит промежуточный).
- `type` коммита — стандартный (см. 5).

**Что можно/нельзя менять в этих подпунктах.**
Список инструментов и порядок работы в этих сценариях —
**живой**: если в proot появляется новая возможность (например,
`ktlint` отдельным бинарём) или на десктопе меняется окружение —
дополнять этот подпункт правкой AGENTS (категория 2 по 5g,
прямой push в `dev`), без отдельной задачи.

**Историческая справка.** В сессиях 2026-10-25 (#3–#8) тип `wip`
использовался в заголовке как стандартный (`wip(domain): ...`).
Это отклонение от 5 (список типов закрытый); переписывать историю
нельзя (force-push, 5a). Впредь — стандартный тип + `WIP` в теле.

### Перед правками

- Ассистент запрашивает актуальные версии файлов, которые
  собирается менять. Не полагается на память о предыдущих
  сессиях.
- **KDoc читать целиком, а не только сигнатуры.** При
  первом касании файла — открыть KDoc класса и функций
  (обычно в шапке файла). KDoc содержит: известные
  ограничения, указатели на другие задачи, предупреждения
  о lifecycle, ловушки. Пропуск KDoc — источник ошибок,
  которые видны только при чтении комментариев. Пример:
  `TInvestOrderStateWebSocket` без stop(),
  `TInvestPricesWebSocket` с incremental subscription
  вместо parity с gRPC — эти решения объяснены в KDoc.
- **Атомарный запрос KDoc + сигнатуры.** Когда нужны
  сигнатуры методов — запрашивать KDoc и сигнатуру
  **одной командой**, а не двумя шагами. Примеры:

      grep -n -B30 -A10 "^\s*fun <name>" <path>
      grep -n -B50 -A10 "^\s*class <name>" <path>

  - `-B` — контекст перед: захватывает KDoc (`/** ... */`).
    `-B30` для метода (KDoc обычно 10–20 строк), `-B50` для
    класса (KDoc 20–40 строк).
  - `-A` — контекст после: сигнатура + первые строки тела.
  - **Несколько целей** — через альтернацию в regex:
    `grep -n -B30 -A10 "^\s*fun <name1>\|^\s*fun <name2>" <path>`.
  - **Шум допустим.** `-B`/`-A` захватывает соседние методы
    и импорты — приоритет KDoc целиком, не чистота вывода.
  - **Файл целиком** — только когда правок много и нужен
    весь контекст (рефакторинг структуры, много методов).
  - **Запрещено** `grep "fun <name>"` без `-B`: KDoc
    пропускается, правило «KDoc читать целиком» нарушается.

  **Почему:** одна команда вместо двух — меньше трафика и
  раундов; KDoc не теряется. Практика 2026-10-23:
  `runGrcpStream` (метод, `-B30`), `OrderFlowManager` (класс,
  `-B50`), альтернация двух методов — всё захватило KDoc
  целиком.
- Перед удалением кода проверяет через `grep`, что он
  действительно не используется.
- Перед переименованием или сменой сигнатуры проверяет всех
  вызывающих.
- **Anchor на строку с отступом — проверять `repr()`.**
  При замене одной строки по anchor (не через многострочный
  блок) — сначала получить точный отступ через
  `repr(line)` / `len(line) - len(line.lstrip())`, потом
  писать anchor. Не по визуальной оценке: `cat -A`
  показывает символы, но количество пробелов легко
  пересчитать неверно. Практика 2026-10-25 (#5
  `AccountsApi`): anchor в
  `TScalpApplication.resolveTInvestAccountId` написан с 20
  пробелами, реально было 16, скрипт упал с
  `anchor count = 0`. Проверка через `repr()` занимает
  5 секунд, откат красной сборки — минуты.
- **Порядок импортов при вставке — по алфавиту, не по
  позиционному anchor.** При добавлении импорта — сначала
  определить место по алфавиту (с учётом ktlint-правил:
  `java`, `javax`, `kotlin` и алиасы в конце), затем
  вставить. Не «после такого-то импорта» — ktlintFormat
  ловит и требует переупорядочивания. Практика 2026-10-25:
  три раза подряд (#1 `StreamsApi`, #2 `BrokerCredentials`
  + `BrokerLifecycleApi`, #3 `BrokerInstrumentApi`) импорт
  вставлялся позиционным anchor'ом и падал на
  `ktlintMainSourceSetCheck`. Решение: сортировать набор
  импортов alphabetically перед вставкой, либо прогонять
  `ktlintFormat` после каждой правки импортов.

### Unit-тесты: mockk для suspend-функций

Для `suspend`-функций в mockk — **только** `coEvery` / `coVerify`
(или `coAnswers`), не `every` / `verify`. На неверную версию
компилятор ругается `Suspension functions can only be called
within coroutine body` — ошибка указывает на строку `verify`,
а не на функцию, что путает.

Правило:
- `suspend fun` → `coEvery { ... } returns ...`, `coVerify { ... }`.
- обычная `fun` (включая `fun ... : Flow<T>`) → `every` / `verify`.

Пример из проекта (`OrderFlowManager`):
- `broker.subscribeOrderState(accountId): Flow<OrderState>` —
  suspend → `coEvery` / `coVerify`.
- `broker.ordersSnapshot(accountId): List<OrderListItem>` —
  suspend → `coEvery` / `coVerify`.
- `repository.subscribeLastPrices(broker, ids): Flow<Pair<String, Double>>`
  — **не** suspend (обычный `fun`) → `every` / `verify`.

При написании теста: посмотреть сигнатуру в исходнике, не
догадываться по имени (`getX`, `subscribeX` — не признак suspend).

**JVM-тесты и `android.util.Log`.** Если production-код в тесте
вызывает `AppLogger` → `android.util.Log`, тест упадёт с
`RuntimeException at Log.java:-1`. Лечится
`testOptions { unitTests.isReturnDefaultValues = true }` в
`app/build.gradle.kts`. Уже включено; причина — в
`docs/gradle-setup.md` → «Unit-тесты».

### Самодостаточность инфраструктурных скриптов

Любой скрипт, Ansible-роль, playbook, Dockerfile или CI-конфиг, который
ассистент пишет или правит, обязан:

- **явно перечислять все зависимости** — пакеты, версии, репозитории,
  сервисы;
- **устанавливать отсутствующее сам**, не полагаясь на «из коробки»;
- **проверять состояние перед изменением** — идемпотентность
  (правило 4d);
- **не оставлять ручных шагов**, которые пользователь должен доделать
  по памяти.

**Запрещено полагаться на:** предустановленные пакеты («обычно podman
уже стоит»), дефолтные настройки ОС («systemd настроен»), неявные
состояния системы, внешние ресурсы без фиксации версии.

**Причина:** в CI, Ansible, развёртывании «из коробки» — источник
скрытых сюрпризов. Скрипт должен воспроизводиться с нуля на чистой
системе, без неявных предпосылок. Проверка «всё поставилось и
работает» — часть задачи, а не опция.

### Git workflow: синхронизация с origin

Для синхронизации локальной ветки с origin используем
**двухшаговую схему**:

    git remote update
    git merge --ff-only origin/<branch>

**Почему не `git pull`:**

- `git pull` = `git fetch` + `git merge` в одной команде.
  Если локальная ветка разошлась с origin, `git pull`
  создаст merge-коммит молча — история станет грязной,
  а причина расхождения — незамеченной.
- `git pull --rebase` перепишет локальные коммиты.
  Тоже нежелательно без явного решения.
- `git remote update` + `git merge --ff-only` разделяет
  операции: сначала обновляем remote-ссылки, потом
  явно решаем, что делать с локальной веткой.
- При `--ff-only` merge **невозможен**, если ветки разошлись.
  Это сигнал разобраться, а не автоматический merge-коммит.

**Порядок:**

1. `git remote update` — обновить все отслеживаемые remote.
2. `git status` — посмотреть, отстаёт / совпадает / разошлась.
3. `git merge --ff-only origin/dev` — fast-forward только
   если возможно.

Если `--ff-only` не прошёл — **остановиться и разобраться**.
Не делать `git pull`, не делать `git merge` без явного
намерения.

**Исключение:** merge feature-ветки в `dev` (не синхронизация) —
через `git merge --no-ff` или через web PR, как зафиксировано
в ROADMAP. Правило выше — только про синхронизацию **текущей
ветки с её origin-копией**.

### Git workflow: ветки и PR

Полное соглашение о ветвлении — в `docs/git-flow.md`. Здесь —
краткая карта для быстрой ориентации.

**Постоянные ветки:**

- `master` — релизы. Прямой push запрещён (Ruleset).
- `dev` — интеграция. Прямой push запрещён (Ruleset).

**Временные ветки:**

- `feature/<name>` — от `dev`. Одна фича.
- `bugfix/<issue-id>` — от `dev`. Один баг в разработке.
- `release/vX.Y.Z` — от `dev`. Стабилизация перед релизом.
- `hotfix/vX.Y.Z` — от тега на `master`. Экстренный фикс.

**Стратегия merge:** Merge commit везде. Squash и Rebase
отключены в Rulesets — стратегия единая (см.
`docs/git-flow.md` → «Осознанные отклонения»).

**Карта merge:**

| Source | Target | Тег |
|---|---|---|
| `feature/*` | `dev` | — |
| `bugfix/*` | `dev` | — |
| `release/*` | `master` | `vX.Y.Z` |
| `master` | `dev` | — |
| `hotfix/*` | `master` | `vX.Y.(Z+1)` |
| `hotfix/*` | `dev` | — |

**Порядок работы над задачей из ROADMAP** — правило 5g.

**Проверка перед PR:** `./gradlew :app:clean
:app:testDebugUnitTest --rerun-tasks` — зелёный. CI прогонит
то же на PR.

### Всё планируемое — в документах

Любое решение, план, улучшение или отложенная идея, о которых
договорились в сессии, **обязаны** быть зафиксированы в
`docs/ROADMAP.md` (или `docs/ISSUES.md` для проблем) в той
же сессии.

Правило действует независимо от того, будут ли они реализованы
сейчас, позже или никогда. Если идея обсуждалась и была принята
к рассмотрению — она попадает в документ с оценкой, вариантами
и обоснованием.

Запрещено держать планы «в голове» или «в истории чата».
История чата не является носителем плана — ею нельзя
воспользоваться через месяц.

Если пользователь предлагает варианты улучшений и просит
их оценить — ассистент обязан предложить конкретную формулировку
для `docs/ROADMAP.md`, а не ограничиваться ответом в чате.

### Диаграммы в документации

Документация проекта обогащается **Mermaid-диаграммами**
постепенно. Правило действует без срочного переписывания
существующих документов — диаграмма добавляется тогда,
когда ассистент касается документа по другой задаче.

**Когда добавлять:**
- при любой правке раздела, который описывает процесс,
  поток данных, последовательность вызовов, состояния или
  зависимости;
- если визуализация сокращает текст (3+ абзаца описания
  процесса → одна диаграмма);
- если без диаграммы читатель вынужден держать в голове
  ветвления или параллельные пути.

**Тип — по задаче:**
- `flowchart` — алгоритмы, каскады, fallback-цепочки;
- `sequenceDiagram` — взаимодействие слоёв, вызовы API;
- `stateDiagram-v2` — состояния и переходы;
- `classDiagram` — структура классов, если она неочевидна;
- `erDiagram`, `gantt`, `gitGraph` — по необходимости.

**Правила оформления:**
- Диаграмма — в том же документе, рядом с описываемым
  разделом. Не в отдельном файле.
- Подпись над диаграммой: одно предложение — что она
  показывает.
- Если диаграмма дублирует текст дословно — оставить
  что-то одно. Обычно текст сокращается до 1-2 предложений
  контекста, детали уходят в диаграмму.
- Не вставлять диаграмму «для красоты»: только если она
  несёт информацию.

**Ограничения ассистента (учитывать при генерации):**
- Mermaid-синтаксис пишется «вслепую» — рендер не проверяется.
  Если результат отрендерится криво, пользователь сообщит.
- Точное позиционирование недоступно — раскладка на Mermaid.
- Для графов >15 узлов возможна тесная раскладка — дробить
  на несколько диаграмм.

**Запрещено:**
- Рисовать диаграммы, которые дублируют текст без потери
  информации (ничего не добавляют).
- Переделывать существующие документы ради добавления
  диаграмм вне задачи — только при касании документа.

**Источник правила:** пользователь (сессия 2026-10-12),
постепенное обогащение документации без срочного переписывания.




### Пометка о мобильной работе

Каждая задача в `docs/ROADMAP.md` получает **пометку о
возможности закрытия с телефона** — сразу после заголовка
`##`, до поля «Статус».

**Рабочее окружение на телефоне:** proot-окружение Ubuntu
в Termux. Доступны полноценный терминал, `git`, `grep`,
`sed`, текстовые редакторы (nano/vim), установка пакетов.
**Недоступны:** Android Studio, эмулятор, локальный запуск
Gradle-сборки (тяжело для proot, нестабильно), подключение
к устройству по ADB.

**Формат:**

    **Мобильная работа:** полное закрытие | частичное | невозможно

**Значения:**

- **полное закрытие** — задача выполняется целиком с
  телефона через proot-терминал: правки в `*.md` и
  конфигах, `git`, push, PR через web. Не требует
  локальной сборки Gradle и IDE.
- **частичное** — часть задачи делается с телефона, часть
  требует десктопа. В скобках — что именно требует
  десктопа: например, `частичное (нужна сборка)`.
- **невозможно** — задача требует запуска Gradle-сборки,
  Android Studio, эмулятора или ADB.

**Зачем:** при переключении на работу с телефона
пользователь сразу видит, какие задачи доступны. Не
тратится время на попытки закрыть то, что физически
нельзя сделать без десктопа.

**Правило распространяется на все новые задачи.**
Существующие задачи размечаются при первом касании
(по правилу обогащения документации — см. «Диаграммы
в документации»).

### Порядок секций в плановых документах

В `docs/ROADMAP.md` и `docs/ci-roadmap.md` — два раздела
с разной сортировкой:

**Планируемые задачи (`## <название>` до `## Закрытые задачи`):**
**порядок выполнения (приоритет)** — сверху вниз. Первая
задача в списке — следующая к выполнению. Новая задача
вставляется в позицию по приоритету относительно
существующих, не в начало раздела. Существующие задачи,
оказавшиеся ниже по приоритету, сдвигаются вниз (к концу
файла) — автоматически становятся менее приоритетными.
Правило «свежее сверху» не действует: свежесть создания
не определяет позицию, определяет приоритет.

**Завершённые задачи (`### ✅ <название>` в разделе
«Закрытые задачи»):** свежие — **снизу**. Линейная
хронологическая лента, читается сверху вниз от старых
к новым. Новое закрытие дописывается в **конец** файла.

**Зачем разные:** планируемые — рабочий список, частота
обращения высокая. Завершённые — архив, читается редко
и целиком (для контекста).

**При сортировке** внутри каждого раздела сохраняется
внутренняя ось: у планируемых «более приоритетное
(следующее к выполнению) → менее приоритетное» сверху
вниз; у завершённых — хронология (старые → новые).

**Разделитель между блоками.** Задачи разделены строкой
`\n\n\n\n---\n` — четыре перевода строки, три дефиса, один
перевод строки. В raw-файле:

    <конец предыдущего блока>
    <пустая>
    <пустая>
    <пустая>
    ---
    <начало нового блока>

Три пустые строки перед `---`, одна после. Скрипты для
вставки новых задач (правило 4c) обязаны соблюдать этот
разделитель — иначе секции «слипаются» и markdown-рендер
ломается.

## Эволюция директив

Этот документ — живой. Правила уточняются по ходу работы,
когда обнаруживаются грабли, находки, повторяющиеся ошибки.

### Правки директив приоритетнее любой деятельности

Правка этого документа (AGENTS.md) — **срочная и неотложная
задача**. Если в ходе работы обнаружено, что правило устарело,
неполно, неоднозначно или противоречит реальности:

1. **Остановить текущую деятельность.**
2. Сформулировать правку (было → стало).
3. Получить согласование.
4. Внести правку в `dev` (docs-only, bypass), отдельным
   коммитом.
5. Только потом — вернуться к прерванной задаче.

**Почему:** неполное/устаревшее правило порождает неверные
решения во всех последующих сессиях. Один раз исправить
правило дешевле, чем N раз ловить его последствия.

**Пример:** схема полей при `mark done` (5g.4) не была
зафиксирована — ассистент удалял `**Подтверждение:**` и
`**Следующий шаг:**` по своему усмотрению. После обнаружения —
правка 5g.4 + это правило, приоритетно, до mark streamstate done.

**Не путать с workflow-находками:** находка (ниже) — про то,
что зафиксировать. Это правило — про **приоритет** фиксации
перед другой работой.

### Workflow-находки фиксируются сразу

Если при работе над задачей обнаружено улучшение workflow
(защитный паттерн, новый assert, способ избежать
повторяющейся ошибки, найденная особенность платформы) —
ассистент **обязан** предложить запись в этот документ
в том же шаге, без отдельной задачи.

**Не откладывать «на потом»:** следующая сессия не вспомнит
контекст. Находка, потерянная между сессиями, — это
потерянная защита от повторения уже совершённой ошибки.

**Отличие от задачи в ROADMAP.** Workflow-находка — не
«работа на будущее», а **защита от повторения уже
совершённой ошибки**. Она должна действовать с момента
обнаружения. Если находка требует рефакторинга кода —
она идёт в ROADMAP; если требует нового правила или
уточнения существующего — она идёт сюда.

**Признак того, что находку надо фиксировать:**

- ошибка была **совершена** (не гипотетическая);
- она **повторяемая** (при похожем контексте повторится);
- её можно **описать как правило** без привязки к конкретной
  задаче.

**Пример.** Trailing whitespace в `docs/*.md`: скрипты
вставки создавали пробелы в конце строк, `assert` падал
с ложным «правка не применилась». Правило «не создавать
trailing spaces, `rstrip()` каждой строки» — зафиксировано
в том же шаге, не отложено.

**Формат:** правка в этот документ + готовый commit message
в том же ответе (правило 5b).

## Коммуникация

- Отвечать на русском, коротко, по делу.
- Если задача неясна — задать уточняющий вопрос, не начинать
  наугад.
- Если ассистент ошибся — признать прямо, без оправданий.
- Если пользователь ошибся — указать тактично, объяснить почему.
