# AGENTS.md — директивы для ИИ-ассистента

Документ описывает правила работы ИИ-ассистента над проектом TScalp
(Android-приложение для торговли через T-Invest, BCS, Finam).
Читается в начале каждой сессии. Применяется без исключений,
кроме случаев, когда пользователь явно отменяет правило.

---

## Стиль работы

### 1. Не менять UI без санкции

Любое изменение, видимое пользователю (тексты, иконки, разметка,
порядок элементов, названия вкладок, цвета), требует явного
согласования **до** внесения правок. Ассистент описывает, что
собирается изменить, получает подтверждение, только затем пишет код.

Изменения в слое данных, логике, ViewModel, репозитории — не
требуют санкции. UI — требует.

### 2. Чистота кода — приоритет

Если для решения задачи требуется переделать что-то «как следует»,
и это больше объёма, чем минимальный фикс — ассистент **обязан**
предложить такой вариант явно. Объём работы не является аргументом
против чистого решения.

Ассистент всегда рассматривает оба варианта (минимальный фикс /
правильное решение) и предлагает пользователю выбрать. Молча
скатываться к костылю — запрещено.

### 2a. Актуальность решений, не традиция

При выборе инструмента, подхода или архитектурного решения
ассистент **обязан** рассматривать и предлагать не только
исторически привычный вариант, но и актуальное состояние
экосистемы на текущий момент.

Конкретно:

- **Проверять актуальность инструмента.** Прежде чем предлагать
  JaCoCo, Retrofit, Mockito, shared preferences, Dagger — ассистент
  проверяет, что это не устаревший дефолт, вытесненный более
  современным решением. Например, для Android/Kotlin в 2026 году:
  Kover вместо JaCoCo, Ktor/OkHttp вместо Retrofit, KSP вместо
  kapt, DataStore вместо SharedPreferences, Hilt (в проекте уже
  есть) вместо Dagger.
- **Не опираться на «так принято».** «Все так делают» — не
  аргумент. Аргумент — «это работает лучше/проще/надёжнее
  здесь и сейчас».
- **Явно указывать альтернативы.** Если есть 2–3 разумных
  варианта, ассистент перечисляет их, отмечает актуальный
  и объясняет выбор.
- **Признавать устаревшие установки.** Если ассистент поймёт,
  что предложил традиционное решение по инерции, а не по
  существу, — он говорит об этом прямо и предлагает
  пересмотреть.
- **Сверяться с датой.** Сессия идёт в 2026 году, не в 2020.
  «Стандарт де-факто» пятилетней давности может быть уже
  legacy.

Правило действует всегда: при выборе библиотек, паттернов,
структуры кода, инструментов CI, форматов данных. Не только
при явном обсуждении стека.

### 2b. Организационные практики — по индустрии

Правило 2a (актуальность решений) действует для прикладного
стека: библиотеки, паттерны, инструменты. Для
**организационного слоя** — CI/CD, ветвления, code review,
релизного цикла — действует отдельный принцип.

**Принцип:** организационные практики воспроизводятся по
актуальным индустриальным стандартам, **даже если часть из
них создаёт overhead сейчас и не имеет потребителя в
текущем масштабе проекта**.

**Почему:** организационный слой — задел под рост команды.
Когда появляется второй разработчик или тестировщик,
перестройка процесса на ходу дороже, чем изначально
воспроизвести индустриальную схему. Плюс: соло-разработка
на индустриальном процессе — это опыт воспроизведения
практики, применимый в командной работе.

**Что попадает под правило:**
- git-flow и стратегии merge (GitHub Flow / GitFlow /
  Trunk-Based);
- защита веток, правила PR, required checks;
- стадии CI-пайплайна (lint → build → test → deliver);
- публикация артефактов (Firebase, Play Store);
- code review через второй аккаунт (role emulation);
- secrets и окружения (Repository vs Environment).

**Как выбирается стандарт:**
- Если есть индустриальный стандарт де-факто (GitFlow,
  GitHub Flow, semantic versioning) — воспроизводим его.
- Если стандарты конкурируют (например, Squash vs Merge
  commit) — выбирается один осознанно, с обоснованием,
  фиксируется в `docs/`.
- Если стандарт конфликтует с текущей настройкой проекта
  (например, Merge commit у нас уже зафиксирован в ROADMAP,
  а GitFlow рекомендует Squash) — решение пересматривается
  явно, а не «оставляем как было».

**Отклонения от стандарта** допускаются, если они
**осознанные и задокументированы** (например, имя ветки
`dev` вместо `develop` — канон GitFlow, но миграция дороже,
чем отклонение). Каждое отклонение — отдельная строка в
`docs/git-flow.md` со ссылкой на причину.

**Не путать с правилом 2a:**
- 2a — «какой инструмент выбрать» (прикладное).
- 2b — «как организовать процесс» (организационное).

### 3. Не выдумывать

Если ассистент не может подтвердить факт (не видит файла,
не знает содержимого ссылки, не уверен в поведении API) — он
говорит об этом прямо. Запрещено генерировать правдоподобные
догадки и выдавать их за факты.

Формулировки «я изучил», «я увидел», «судя по вашим файлам»
допустимы только тогда, когда содержимое действительно было
передано в текущей сессии.

### 4. Маленькие шаги с проверкой

Одна задача — один логически завершённый шаг. Между шагами —
сборка (`./gradlew :app:clean :app:testDebugUnitTest --rerun-tasks \
      2>&1 | grep -E '\[warn\]|\[error\]|^w:|^e:'`)
и проверка, что тесты зелёные и новых ошибок компиляции нет.
Фильтр `grep` нужен, потому что Gradle 9.x показывает
Kotlin compiler warnings через Problems API (HTML-отчёт +
секция `[warn]`) вместо привычного `w: file:///`. Без фильтра
warning'и тонут в служебном выводе. Проверяем, что тесты зелёные
и новых ошибок компиляции нет.

Крупные задачи дробятся на подшаги. Например: добавить метод в
репозиторий → скомпилировать → мигрировать вызывающего →
скомпилировать → удалить старый метод → скомпилировать.

Если задача слишком большая для одного сообщения — ассистент
предлагает разбивку, не пытается выдать всё сразу.

### 4a. Формат показа правок

Правки кода показываются в формате **«было → стало»**, не diff'ом.
Diff'ы неудобны для чтения с телефона и требуют мысленного
восстановления контекста.

Формат:

**Файл:** `путь/к/файлу.kt`, строка N

**Было:**
```kotlin
<старый фрагмент>
```
**Стало:**
```kotlin
<новый фрагмент>
```
Если правка мелкая (одна строка, замена имени) — «было-стало»
в одну строку через → допустимо.

При массовых однотипных правках (например, апгрейд версии в
нескольких местах) — таблица: «файл / было / стало».

Diff (- / +) остаётся допустим только для .gitlab-ci.yml,
.md и конфигов, если пользователь явно попросит.

**Вложенные markdown-блоки — правило N+1.**

Если правка содержит markdown-разметку — заголовки `###`,
жирный `**`, горизонтальные линии `---`, code-блоки с
тройными backticks — ассистент оборачивает текст правки во
**внешний блок обратных кавычек**. Количество внешних
кавычек = **максимальная длина вложенной последовательности
backticks + 1**, но не менее 3.

**Типичные случаи:**

- Внутри только одиночные backticks (inline code) → внешняя 3
  (стандартный code-блок).
- Внутри есть тройные backticks (code-блоки) → внешняя 4.
- Внутри есть четыре backticks (правка про markdown) →
  внешняя 5.
- И так далее.

**Зачем:** ассистент не видит отрендеренный ответ. Без
корректной внешней обёртки его markdown-разметка
превращается в заголовки/жирный/линии прямо в чате, и
пользователь не может скопировать raw-текст для вставки
в файл. N+1 гарантирует, что внутренние последовательности
backticks не закроют внешний блок раньше времени.

**Запрещено** использовать обёртку той же длины, что и
максимальная вложенная — она сломается на первом же
внутреннем backtick такой же длины.

**Правило действует для:** правок `.md`-файлов, примеров
markdown в ответах, любых фрагментов, где разметка должна
сохраниться дословно.

**Не путать с обычными code-блоками.** Правки `.kt`, `.kts`,
`.yml` не содержат тройных backticks внутри — им хватает
стандартной обёртки из 3. Правило N+1 касается только тех
случаев, где внутри правки встречаются тройные backticks.
Правило снимает этот класс ошибок.

### 4b. Один шаг за раз

При работе над задачей ассистент выдаёт **одну подзадачу
(шаг) за раз** и **останавливается**. Следующий шаг — только
после явного «дальше» / «ок» / «продолжай» от пользователя.

**Запрещено:**

- Выдавать простыню «шаг 1 → шаг 2 → … → шаг N» в одном
  ответе, даже если все шаги очевидны.
- Начинать следующий шаг самостоятельно, без подтверждения.
- Прятать в конце ответа формулировки «а затем сделай …»,
  «после этого …», «дальше идём на …» — это неявный толчок
  вперёд, эквивалентный выдаче нескольких шагов.

**Формат ответа на каждом шаге:**

1. Что делаем сейчас — одно предложение.
2. Правки в формате «было → стало» (см. 4a).
3. Команды для проверки (сборка / тесты / что угодно).
4. Одна строка: «Останавливаюсь. Жду результата / „дальше“».

**Исключение:** пользователь явно просит полный план
(например, «распиши все шаги», «составь план»). Тогда
ассистент выдаёт план целиком — но как **план**,
без выполнения. Выполнение всё равно идёт по шагам.

**Разделение понятий:**

- **План** (в `docs/ROADMAP.md` или по явному запросу) —
  все шаги сразу, самодостаточно (см. 5e).
- **Ведение по задаче** (в чате, при реализации) — по одному
  шагу, с остановкой после каждого.

Эти два режима не смешиваются.

**Причина:** пользователь должен успеть проверить результат
шага и решить, продолжать ли. Особенно на телефоне, где
каждая правка требует внимательного прочтения, а автофикс
или массовый рефакторинг может задеть неожиданные места.

### 4c. Механические правки — скриптом

Если правка описывается **механически** — «заменить X на Y»,
«удалить блок между маркерами», «вставить перед строкой Z»,
«массовая замена по всем файлам» — ассистент **обязан**
давать готовую команду (`sed`, `python3` через heredoc,
`awk`), а не текст «найди и вставь руками».

**Когда команда:**

- Замена по маркеру: `### Заголовок` → `### Новый заголовок`.
- Удаление секции по границам (от `### X` до `---` перед
  следующим `### Y`).
- Вставка блока в определённое место.
- Массовые однотипные замены.
- Схлопывание дублирующихся пустых строк / `---` / пробелов.

**Когда только текст:**

- Пользователь явно попросил «пришли текст, я сам поправлю».
- Правка интерактивная — решения принимаются по ходу.
- Много мелких вставок в разных местах, где скрипт окажется
  длиннее текста.

**Общий принцип:** если правка механически описывается —
команда. Если это вставка новой секции целиком — тоже
команда (heredoc + append или вставка по маркеру).

**Зачем:** команда не оставляет места для ошибок «не туда
вставил», «не то удалил», «потерял строку при копировании».
Особенно важно для больших `.md`-файлов, где ручное
редактирование через экран телефона — источник опечаток.

**Примеры формата:**

Удаление секции по маркерам:

    python3 <<'PYEOF'
    from pathlib import Path
    p = Path("docs/ROADMAP.md")
    lines = p.read_text(encoding="utf-8").splitlines(keepends=True)
    start = next(i for i, l in enumerate(lines)
                 if l.startswith("### Каскад обновления позиций"))
    end = next(i for i, l in enumerate(lines) if i > start
               and l.startswith("### Переход на edge-to-edge"))
    p.write_text("".join(lines[:start] + lines[end:]),
                 encoding="utf-8")
    PYEOF

Вставка секции перед маркером:

    python3 <<'PYEOF'
    from pathlib import Path
    p = Path("docs/ROADMAP.md")
    text = p.read_text(encoding="utf-8")
    marker = "### Рефакторинг расчёта P&L"
    new_block = """### Новая задача

    **Статус:** запланировано.
    ...
    """
    p.write_text(text.replace(marker, new_block + marker, 1),
                 encoding="utf-8")
    PYEOF

**Не путать с 4a.** 4a — про то, как показывать текст
правки пользователю в чате. 4c — про то, каким способом
вносить правку в файл: командой или вручную.

### 4d. Идемпотентность операций

Операции, которые ассистент предлагает для исполнения
(скрипты для правок файлов, `git mv`, `git remote remove`,
создание тегов, удаление секций), должны быть
**идемпотентными** или **явно проверять предусловие**.

**Зачем:** пользователь не всегда уверен, что операция
применилась. Повторный запуск не должен дублировать
код, портить файл или молча ничего не делать — он должен
либо дать тот же результат, либо явно упасть с сообщением
"уже применено" / "не найдено".

**Три паттерна для скриптов правок:**

**Паттерн 1 — assert на маркер отсутствия.**

Перед вставкой нового блока:

    assert "@Preview" not in text, "Превью уже добавлены"

Если маркер уже есть — скрипт упадёт, а не вставит
дубликат.

**Паттерн 2 — assert на существование + замена с count=1.**

Перед заменой фрагмента:

    assert old_fragment in text, "Заменяемый фрагмент не найден"
    text = text.replace(old_fragment, new_fragment, 1)

Если фрагмент уже заменён — assert не пройдёт, потому
что old_fragment в файле больше нет.

**Паттерн 3 — проверка после записи.**

    p.write_text(text, encoding="utf-8")
    assert new_marker in p.read_text(encoding="utf-8"), \
        "Правка не применилась"

Проверяет, что запись действительно произошла.

**Запрещено в скриптах правок:**

- Append без проверки (`text += new_block` в цикле
  повторов).
- `replace(...)` без `count=1`, если шаблон может
  встретиться несколько раз.
- Молчаливый `try/except` вокруг записи — пользователь
  должен узнать об ошибке.
- Использовать `assert` только как «отладку» без
  сообщения. Сообщение в assert — часть UX: оно
  подсказывает, что пошло не так.

**Для операций с git:**

- `git branch -d <name>` — сам по себе безопасен,
  упадёт если ветка не смержена.
- `git remote remove <name>` — идемпотентен не сам
  по себе, но перед ним ассистент проверяет
  `git remote -v` и при отсутствии говорит
  «remote уже удалён».
- `git push origin --delete <branch>` — падает с
  ошибкой, если ветка уже удалена; ассистент
  проверяет `git ls-remote --heads origin <name>`
  перед командой.

**Правило действует для всех операций, которые
предлагает ассистент.** Если идемпотентность
недостижима (например, «удалить последний коммит»),
ассистент явно предупреждает: «операция не
идемпотентна, выполняй один раз».

**Проверочный маркер должен появляться именно после
правки.** Если в `assert ... in text` используется строка,
которая никогда не будет в файле (даже после успешной
записи), — проверка бесполезна: пропускает и ложно-
положительный, и ложно-отрицательный результат.

Правильный маркер — уникальная подстрока из вставляемого
блока (например, имя первой новой функции, уникальное
имя поля, отпечаток новой секции). Не из общих слов.

**Пример ошибки:** вставляется функция
`BrokerAccountDialogTInvestPreview`, а проверяется
наличие `BrokerAccountDialogPreview` — подстрока
не совпадает, проверка проходит вхолостую.

**Правильно:** проверять `BrokerAccountDialogTInvestPreview`
или `@Preview(name = "T-Invest — with accounts"`.

### 5. Коммит после каждой задачи

Как только задача завершена и проверена (сборка зелёная,
на устройстве работает) — ассистент предлагает коммит с готовым
сообщением в стиле:

`<type>(<scope>): <краткое описание>`

`<тело: что изменилось и почему>`

Типы: `feat`, `fix`, `refactor`, `chore`, `docs`, `test`.

**Язык коммитов — только английский.** Заголовок и тело.
Русский в commit message запрещён, даже если обсуждение задачи
идёт на русском.

**Правило распространяется на все текстовые артефакты
репозитория:** commit message, тело PR/MR, комментарии
в PR/MR, сообщения тегов, release notes, код-ревью.
Всё, что остаётся в истории и доступно другим —
на английском.

Чат с пользователем — на русском (см. «Коммуникация»).
Граница проходит по репозиторию, а не по теме обсуждения.

Коммит — точка отката. Не коммитить «в конце дня» пачкой.

Исключение: если работа идёт с устройства без доступа к
терминалу (телефон, веб-интерфейс GitLab без локального
репозитория) — допустимо накапливать изменения и закоммитить
одним блоком при первой возможности. Такой блок в commit
message должен быть явно разделён на смысловые части в теле
(разделы `- area: ...`), даже если физически это один коммит.

### 5a. Порядок коммита: локально vs CI

**Локальные изменения** (код, ресурсы, Gradle-конфиги, документация):
коммит **после** зелёной сборки
`./gradlew :app:clean :app:testDebugUnitTest --rerun-tasks`.
Если сборка падает — сначала фикс, потом коммит.

**CI/CD изменения** (`.gitlab-ci.yml`, CI-скрипты, конфиги пайплайна):
коммит **до** проверки. Пайплайн не воспроизводится локально,
поэтому порядок обратный:
1. внести правку;
2. закоммитить;
3. запушить и дождаться результата пайплайна;
4. пайплайн зелёный → следующий шаг;
5. пайплайн красный → фикс **отдельным коммитом** (не `--amend`,
   не force-push в `master`/`dev`).

**Смешанные изменения** (код + CI в одной задаче) — **два коммита**,
по одному на область. Не смешивать.

**Общий принцип:** один коммит — одна задача. Дробление на этапы
приветствуется, лишь бы каждый коммит был логически завершён и
точка отката была осмысленной.

### 5b. Правки в docs — сразу с коммитом

Любая правка в `docs/` или `AGENTS.md` сопровождается готовым
сообщением для коммита в том же ответе ассистента. Не отдельным шагом «скажи, когда
закоммитишь», не «пришлю сообщение позже».

Формат ответа для каждого документа — **один блок**:

1. Файл, было/стало.
2. Готовый commit message.
3. Одна строка — что делать дальше.

Если правится несколько документов (`AGENTS.md` +
`docs/ROADMAP.md`, `docs/ROADMAP.md` + `docs/ISSUES.md`
и т.п.) — **отдельный блок
на каждый документ**, каждый со своим commit message.
Это разные задачи, коммиты не смешиваются.

Запрещено выносить commit message в отдельный блок
ответа — «сначала все правки, потом все коммиты».
Правка и её коммит — атомарная пара.

Правило действует для всех документов проекта.

### 5c. Структура ответа

Ответ собирается из стандартных блоков. Применяются
по необходимости — не раздувать.

1. **Диагностика.** Что проверено, что видно, чего не видно.
2. **Варианты.** Если 2+ разумных решения — перечислить
   с плюсами и минусами.
3. **Рекомендация.** Какой вариант и почему.
4. **Правки.** Формат «было → стало» (см. 4a).
5. **Коммит-сообщение.** Готовый текст (см. 5b).
6. **Порядок.** Что делать сейчас, что потом.

Пустые блоки опускаются. Тривиальная задача (одна строка,
опечатка) — только 4 и 5.

### 5d. Жизненный цикл задачи

Для задач, зафиксированных в ROADMAP, применяется
трёхфазный цикл.

**Фаза 1 — открытие.**

Ответ содержит блоки 1–3 (диагностика, варианты,
рекомендация). Ассистент **ждёт утверждения** от
пользователя. Только после «да» — коммит:

    docs(roadmap): plan <название>

В теле: что планируется, зачем, варианты, выбранный подход,
оценка.

**Фаза 2 — реализация.**

Начинается **после** коммита плана. Каждый шаг — блоки 4–6
(правки, коммит, порядок). Между шагами — сборка (п. 4).
Один логически завершённый шаг — один коммит.

**Фаза 3 — закрытие.**

Финальный коммит по коду (если ещё не сделан). Затем коммит
в ROADMAP:

    docs(roadmap): mark <название> done

Секция переносится в раздел «Закрытые задачи» в формате
`### ✅ <Название>` с кратким описанием результата.

Отменённые задачи:

    docs(roadmap): mark <название> cancelled

Причина — в теле коммита.

**Тривиальные задачи** (одна строка, опечатка, правка
параметра) — цикл не применяется. Один коммит.

**Пример:**

1. Ответ: диагностика + варианты A/B + рекомендация A.
2. Пользователь: «A».
3. Коммит `docs(roadmap): plan <задача>`.
4. Ответ: правки «было → стало», коммит `chore(...): ...`.
5. Ответ: правки, коммит.
6. Коммит `docs(roadmap): mark <задача> done`.

### 5e. Самодостаточность планов

Любой план, зафиксированный в `docs/ROADMAP.md`,
`docs/ISSUES.md` или в коммите типа
`docs(roadmap): plan ...`, должен быть
**самодостаточным**: другой ассистент (человек или агент)
без доступа к истории чата обязан уметь его реализовать
по одному только описанию.

**Обязательные поля записи:**

- **Статус:** запланировано / в работе / отложено.
- **Контекст:** зачем задача, какую проблему решает.
- **Предусловия:** что должно быть сделано до начала
  (какие задачи, какие обновления SDK, какие санкции).
- **Файлы:** конкретные пути и классы, которые будут
  затронуты. Если файл ещё не создан — указать, где
  его создать.
- **Шаги:** пронумерованная последовательность действий.
  Один шаг — одно логически завершённое изменение.
- **Референсы:** ссылки на SDK, официальную документацию,
  примеры в репозитории, related-файлы в самом проекте.
- **Ограничения:** что нельзя делать, известные грабли,
  антипаттерны, которых избегаем.
- **Критерий готовности:** как проверить, что задача
  выполнена (какое поведение должно наблюдаться,
  какие тесты должны проходить).
- **Оценка:** время в часах или минутах.
- **Зависимости:** какие задачи блокируют эту,
  какие блокируются этой.
- **Открытые вопросы:** факты, которых не хватает
  для реализации (имя метода, формат сообщения,
  состав полей proto). Каждый — с указанием, где
  искать ответ.

**Запрещено в описании плана:**

- Ссылаться на «как обсуждали в чате», «см. выше»,
  «тот же подход, что для задачи X».
- Оставлять шаг без указания файла, в котором он
  делается.
- Указывать в «Референсах» URL без пояснения, что
  именно там смотреть.
- Формулировать шаги в стиле «доработать каскад» без
  конкретики — что именно и где.

**Правило действует для всех документов проекта.**

### 5f. Post-PR checklist

После сообщения пользователя «PR смержен» / «MR смержен» /
«merged» ассистент **обязан**:

1. **Остановиться.** Не переходить к следующей задаче,
   не предлагать «следующий шаг».
2. **Выдать чек-лист post-PR** (см. ниже) и ждать
   подтверждения пользователя по каждому пункту.
3. Только после выполнения чек-листа — переходить к
   следующей задаче.

**Чек-лист post-PR:**

1. Удалить локальную ветку:
   `git branch -d <branch>` (или `-D`, если ветка была
   перебазирована и `-d` отказывается удалять).
2. Удалить удалённую ветку: `git push origin --delete <branch>`.
   Если GitHub/GitLab удалили ветку автоматически при merge —
   шаг пропускается, но это нужно **явно проверить**
   (`git branch -r` — ветки не должно быть).
3. Переключиться на основную ветку: `git checkout dev`.
4. Синхронизировать: `git remote update` +
   `git merge --ff-only origin/dev`.
5. Проверить: `git status` — working tree clean,
   ветка не отстаёт и не опережает origin.
6. Если задача из `docs/ROADMAP.md` — перенести секцию
   в «Закрытые задачи» (см. 5d, фаза 3).

**Формат ответа ассистента после «PR смержен»:**

    PR смержен. Выполняем post-PR чек-лист:

    1. Удалить локальную ветку: `git branch -d <branch>`
    2. Удалить удалённую: `git push origin --delete <branch>`
       (или проверь `git branch -r`, если GitHub удалил автоматом)
    3. `git checkout dev`
    4. `git remote update && git merge --ff-only origin/dev`
    5. `git status`

    Останавливаюсь. Жду вывода команд.

**Запрещено:**

- Пропускать post-PR чек-лист «потому что очевидно».
- Объединять его с началом следующей задачи.
- Выдавать «следующий шаг» до выполнения чек-листа.

**Причина:** post-PR гигиена — не часть продуктивной
работы, а обязательный ритуал синхронизации. Без
формального чек-листа шаги выпадают из внимания
и накапливаются расхождения между локальной и
удалённой историей.

### 5g. Работа с задачами в ROADMAP

**Куда коммитить документацию.** Документация проекта
делится на три категории по связи с задачей. Порядок
коммита — по правилу 5b (правка + готовое сообщение в
одном ответе).

1. **Связанная с feature/bugfix** — KDoc новой функции,
   изменения в справочниках, если фича их затрагивает.
   Куда: feature-ветка, коммит `docs(<scope>): <описание>`.

2. **Не связанная ни с одной задачей** — правка AGENTS.md,
   структурные изменения документации, плановые правки
   ROADMAP вне контекста задачи.
   Куда: короткоживущая ветка `docs/<topic>`, PR → merge
   в `dev`.

3. **Срочное мелкое** — фикс опечатки, правка заголовка.
   Куда: bypass для Repository admin, прямой push в `dev`.
   Если появится второй разработчик без bypass — правило
   пересматривается.

**Особый случай: `docs/ROADMAP.md` и `docs/ci-roadmap.md`.**

Планы — глобальная сущность. Плановые правки (новая идея,
перестановка приоритетов, пересмотр формулировки) — это
категория 2 (docs/<topic> ветка). Feature-ветки их не
таскают.

**Исключение — метаданные о ходе работы над задачей.** Старт
и завершение задачи — часть самой задачи, идут в feature
(см. жизненный цикл ниже).

**Структура файлов:**

- `## Планируемые задачи` — открытые. Свежие сверху.
- `## Закрытые задачи` — принятые. Свежие снизу.

**Жизненный цикл задачи:**

1. **Создание** (руководитель). Задача добавляется в
   `## Планируемые задачи`, статус «запланировано», поле
   «Мобильная работа» заполнено. Коммит в `dev`:
   `docs(roadmap): plan <task>`.

2. **Старт** (исполнитель). Коммит в `dev`:
   `docs(roadmap): start <task>`. Поле «Статус» меняется
   на «в работе», добавляется строка `**Ветка:** feat/<name>`.

3. **Работа** (исполнитель). Feature-ветка создаётся от
   `dev`. Коммиты по коду — обычные, ROADMAP не трогается.

4. **Завершение** (исполнитель). Финальный коммит в
   feature-ветке: `docs(roadmap): mark <task> done`.
   Секция переносится из `## Планируемые задачи` в
   `## Закрытые задачи`, заголовок меняется на
   `### ✅ <название>`, поле `**Ветка:**` удаляется.

5. **Приёмка** (руководитель). Merge PR = принятие. После
   merge в `dev` задача уже в `## Закрытые задачи`
   (перенос сделан feature-веткой). Отдельного коммита
   после merge **не делается**.

6. **Отклонение** (руководитель). Редкий сценарий. PR
   отклоняется, коммит в `dev`:
   `docs(roadmap): return <task> to work` (или
   `abandon <task>`, если задача отменяется). Задача
   возвращается в `## Планируемые задачи` со статусом
   «в работе» и сохраняет `**Ветка:**`.

**Разделение ролей:**

- **Исполнитель** не ставит статус «принято». Он доводит
  задачу до готовности: финальный коммит переносит её
  в `## Закрытые`. Это декларация «готово к приёмке».
- **Руководитель** подтверждает приёмку фактом merge.
  Если merge не сделан — задача не принята.

**После GitFlow** (см. `docs/ci-roadmap.md` → «Переход на
полный GitFlow») этот регламент переносится в
`docs/git-flow.md` и дополняется спецификой release- и
hotfix-веток.

## Работа с кодом

### Проект

- **Стек:** Kotlin, Jetpack Compose, Hilt, Coroutines/Flow,
  gRPC (T-Invest SDK), REST (BCS, Finam).
- **Слои:** `presentation → domain → data`. ViewModel не ходит
  к брокеру напрямую — только через `InvestRepository`.
- **Обработка ошибок:** `AppResult<T>` (Success/Failure), не
  исключения на границах слоёв. Ошибки брокеров расшифровываются
  через `BrokerErrorMessages`.
- **Логирование:** `AppLogger`, не `android.util.Log`.
- **Цены** — только через `PriceStreamManager`. Не вызывать
  `broker.subscribeLastPrices` и `repository.getLastPricesResult`
  из ViewModel напрямую. Регистрировать интерес через
  `setInterest(PriceConsumer, uids)`.

### Идентификаторы инструментов

- **Domain-слой** оперирует `tscalpInstrumentId` — универсальным
  идентификатором инструмента. В domain-моделях, usecase'ах и
  domain-API (`PriceStreamManager`, `PositionStreamManager`)
  ключ инструмента называется `tscalpInstrumentId`, а не `uid`
  и не `figi`.
- **Data-слой** (`data/api/*`, `data/repository/*`) — на границе
  с брокером. Здесь `uid` (T-Invest), `figi` (BCS),
  `ticker` + `exchange` (Finam) честно отражают формат брокера.
- **Трансляция** `tscalpInstrumentId ↔ broker-specific-id`
  происходит в репозитории или в брокере.
- **`InstrumentUi.ttech_uid`** — исключение: специфика T-Invest,
  задокументирована в KDoc поля.

### Перед правками

- Ассистент запрашивает актуальные версии файлов, которые
  собирается менять. Не полагается на память о предыдущих
  сессиях.
- Перед удалением кода проверяет через `grep`, что он
  действительно не используется.
- Перед переименованием или сменой сигнатуры проверяет всех
  вызывающих.

### После правок

- Сборка: `./gradlew :app:clean :app:testDebugUnitTest --rerun-tasks 2>&1 | grep -E '\[warn\]|\[error\]|^w:|^e:'`
- Ожидаемый результат: 63 теста зелёных, только известные
  warning'и (список — в `docs/ISSUES.md`).
- Новые warning'и, новые ошибки — разбираются, не игнорируются.

### Git workflow: синхронизация с origin

Для синхронизации локальной ветки с origin используем
**двухшаговую схему**:

    git remote update
    git merge --ff-only origin/<branch>

**Почему не `git pull`:**

- `git pull` = `git fetch` + `git merge` в одной команде.
  Если локальная ветка разошлась с origin, `git pull`
  создаст merge-коммит молча — история станет грязной,
  а причина расхождения — незамеченной.
- `git pull --rebase` перепишет локальные коммиты.
  Тоже нежелательно без явного решения.
- `git remote update` + `git merge --ff-only` разделяет
  операции: сначала обновляем remote-ссылки, потом
  явно решаем, что делать с локальной веткой.
- При `--ff-only` merge **невозможен**, если ветки разошлись.
  Это сигнал разобраться, а не автоматический merge-коммит.

**Порядок:**

1. `git remote update` — обновить все отслеживаемые remote.
2. `git status` — посмотреть, отстаёт / совпадает / разошлась.
3. `git merge --ff-only origin/dev` — fast-forward только
   если возможно.

Если `--ff-only` не прошёл — **остановиться и разобраться**.
Не делать `git pull`, не делать `git merge` без явного
намерения.

**Исключение:** merge feature-ветки в `dev` (не синхронизация) —
через `git merge --no-ff` или через web PR, как зафиксировано
в ROADMAP. Правило выше — только про синхронизацию **текущей
ветки с её origin-копией**.

### Git workflow: ветки и PR

Полное соглашение о ветвлении — в `docs/git-flow.md`. Здесь —
краткая карта для быстрой ориентации.

**Постоянные ветки:**

- `master` — релизы. Прямой push запрещён (Ruleset).
- `dev` — интеграция. Прямой push запрещён (Ruleset).

**Временные ветки:**

- `feature/<name>` — от `dev`. Одна фича.
- `bugfix/<issue-id>` — от `dev`. Один баг в разработке.
- `release/vX.Y.Z` — от `dev`. Стабилизация перед релизом.
- `hotfix/vX.Y.Z` — от тега на `master`. Экстренный фикс.

**Стратегия merge:** Merge commit везде. Squash и Rebase
отключены в Rulesets — стратегия единая (см.
`docs/git-flow.md` → «Осознанные отклонения»).

**Карта merge:**

| Source | Target | Тег |
|---|---|---|
| `feature/*` | `dev` | — |
| `bugfix/*` | `dev` | — |
| `release/*` | `master` | `vX.Y.Z` |
| `master` | `dev` | — |
| `hotfix/*` | `master` | `vX.Y.(Z+1)` |
| `hotfix/*` | `dev` | — |

**Порядок работы над задачей из ROADMAP** — правило 5g.

**Проверка перед PR:** `./gradlew :app:clean
:app:testDebugUnitTest --rerun-tasks` — зелёный. CI прогонит
то же на PR.

### Всё планируемое — в документах

Любое решение, план, улучшение или отложенная идея, о которых
договорились в сессии, **обязаны** быть зафиксированы в
`docs/ROADMAP.md` (или `docs/ISSUES.md` для проблем) в той
же сессии.

Правило действует независимо от того, будут ли они реализованы
сейчас, позже или никогда. Если идея обсуждалась и была принята
к рассмотрению — она попадает в документ с оценкой, вариантами
и обоснованием.

Запрещено держать планы «в голове» или «в истории чата».
История чата не является носителем плана — ею нельзя
воспользоваться через месяц.

Если пользователь предлагает варианты улучшений и просит
их оценить — ассистент обязан предложить конкретную формулировку
для `docs/ROADMAP.md`, а не ограничиваться ответом в чате.

### Диаграммы в документации

Документация проекта обогащается **Mermaid-диаграммами**
постепенно. Правило действует без срочного переписывания
существующих документов — диаграмма добавляется тогда,
когда ассистент касается документа по другой задаче.

**Когда добавлять:**
- при любой правке раздела, который описывает процесс,
  поток данных, последовательность вызовов, состояния или
  зависимости;
- если визуализация сокращает текст (3+ абзаца описания
  процесса → одна диаграмма);
- если без диаграммы читатель вынужден держать в голове
  ветвления или параллельные пути.

**Тип — по задаче:**
- `flowchart` — алгоритмы, каскады, fallback-цепочки;
- `sequenceDiagram` — взаимодействие слоёв, вызовы API;
- `stateDiagram-v2` — состояния и переходы;
- `classDiagram` — структура классов, если она неочевидна;
- `erDiagram`, `gantt`, `gitGraph` — по необходимости.

**Правила оформления:**
- Диаграмма — в том же документе, рядом с описываемым
  разделом. Не в отдельном файле.
- Подпись над диаграммой: одно предложение — что она
  показывает.
- Если диаграмма дублирует текст дословно — оставить
  что-то одно. Обычно текст сокращается до 1-2 предложений
  контекста, детали уходят в диаграмму.
- Не вставлять диаграмму «для красоты»: только если она
  несёт информацию.

**Ограничения ассистента (учитывать при генерации):**
- Mermaid-синтаксис пишется «вслепую» — рендер не проверяется.
  Если результат отрендерится криво, пользователь сообщит.
- Точное позиционирование недоступно — раскладка на Mermaid.
- Для графов >15 узлов возможна тесная раскладка — дробить
  на несколько диаграмм.

**Запрещено:**
- Рисовать диаграммы, которые дублируют текст без потери
  информации (ничего не добавляют).
- Переделывать существующие документы ради добавления
  диаграмм вне задачи — только при касании документа.

**Источник правила:** пользователь (сессия 2026-10-12),
постепенное обогащение документации без срочного переписывания.




### Пометка о мобильной работе

Каждая задача в `docs/ROADMAP.md` получает **пометку о
возможности закрытия с телефона** — сразу после заголовка
`##`, до поля «Статус».

**Рабочее окружение на телефоне:** proot-окружение Ubuntu
в Termux. Доступны полноценный терминал, `git`, `grep`,
`sed`, текстовые редакторы (nano/vim), установка пакетов.
**Недоступны:** Android Studio, эмулятор, локальный запуск
Gradle-сборки (тяжело для proot, нестабильно), подключение
к устройству по ADB.

**Формат:**

    **Мобильная работа:** полное закрытие | частичное | невозможно

**Значения:**

- **полное закрытие** — задача выполняется целиком с
  телефона через proot-терминал: правки в `*.md` и
  конфигах, `git`, push, PR через web. Не требует
  локальной сборки Gradle и IDE.
- **частичное** — часть задачи делается с телефона, часть
  требует десктопа. В скобках — что именно требует
  десктопа: например, `частичное (нужна сборка)`.
- **невозможно** — задача требует запуска Gradle-сборки,
  Android Studio, эмулятора или ADB.

**Зачем:** при переключении на работу с телефона
пользователь сразу видит, какие задачи доступны. Не
тратится время на попытки закрыть то, что физически
нельзя сделать без десктопа.

**Правило распространяется на все новые задачи.**
Существующие задачи размечаются при первом касании
(по правилу обогащения документации — см. «Диаграммы
в документации»).

### Порядок секций в плановых документах

В `docs/ROADMAP.md` и `docs/ci-roadmap.md` — два раздела
с разной сортировкой:

**Планируемые задачи (`## <название>` до `## Закрытые задачи`):**
свежие — **сверху**. Самое актуальное на виду, не требует
скролла. Новая задача добавляется в **начало** раздела
(сразу после шапки, до других открытых).

**Завершённые задачи (`### ✅ <название>` в разделе
«Закрытые задачи»):** свежие — **снизу**. Линейная
хронологическая лента, читается сверху вниз от старых
к новым. Новое закрытие дописывается в **конец** файла.

**Зачем разные:** планируемые — рабочий список, частота
обращения высокая. Завершённые — архив, читается редко
и целиком (для контекста).

**При сортировке** внутри каждого раздела сохраняется
внутренняя ось: у планируемых «более актуальное → менее
актуальное» сверху вниз; у завершённых — хронология
(старые → новые).

**Разделитель между блоками.** Задачи разделены строкой
`\n\n\n\n---\n` — четыре перевода строки, три дефиса, один
перевод строки. В raw-файле:

    <конец предыдущего блока>
    <пустая>
    <пустая>
    <пустая>
    ---
    <начало нового блока>

Три пустые строки перед `---`, одна после. Скрипты для
вставки новых задач (правило 4c) обязаны соблюдать этот
разделитель — иначе секции «слипаются» и markdown-рендер
ломается.
