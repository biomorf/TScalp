## Документы проекта

- **`AGENTS-LESSONS.md`** — уроки из инцидентов. Шаблон записи
  в самом файле: правило / инцидент / как проверить. Уроки
  сгруппированы по темам; новая запись — в соответствующий
  раздел (см. `## Структура файла` в самом файле). Читается
  вместе с `AGENTS.md` в начале каждой сессии.
- **`docs/ROADMAP.md`** — план задач разработки: код,
  архитектура, data-слой, UI, рефакторинг. Что запланировано,
  что в работе, что отложено. Обновляется по ходу работы.
- **`docs/ci-roadmap.md`** — план организационных задач:
  CI/CD, ветвление, релизный процесс, code quality (ktlint,
  detekt, Kover), публикация артефактов, secrets, environment.
- **`docs/ISSUES.md`** — известные проблемы и отложенные
  решения. Формат записи — в самом файле.
- **`docs/`** — справочные материалы (стримы, настройка
  Gradle, релиз-процесс).

Если возникает вопрос «а это где записано?» — сначала
проверяем эти документы, потом спрашиваем пользователя.

### [AGENTS] project-docs-all-planned Всё планируемое — в документах
<a id="project-docs-all-planned"></a>
Любое решение, план, улучшение или отложенная идея, о которых
договорились в сессии, **обязаны** быть зафиксированы в
`docs/ROADMAP.md` (или `docs/ISSUES.md` для проблем) в той
же сессии.

Правило действует независимо от того, будут ли они реализованы
сейчас, позже или никогда. Если идея обсуждалась и была принята
к рассмотрению — она попадает в документ с оценкой, вариантами
и обоснованием.

Запрещено держать планы «в голове» или «в истории чата».
История чата не является носителем плана — ею нельзя
воспользоваться через месяц.

Если пользователь предлагает варианты улучшений и просит
их оценить — ассистент обязан предложить конкретную формулировку
для `docs/ROADMAP.md`, а не ограничиваться ответом в чате.

### [AGENTS] project-docs-diagrams Диаграммы в документации
<a id="project-docs-diagrams"></a>
Документация проекта обогащается **Mermaid-диаграммами**
постепенно. Правило действует без срочного переписывания
существующих документов — диаграмма добавляется тогда,
когда ассистент касается документа по другой задаче.

**Когда добавлять:**
- при любой правке раздела, который описывает процесс,
  поток данных, последовательность вызовов, состояния или
  зависимости;
- если визуализация сокращает текст (3+ абзаца описания
  процесса → одна диаграмма);
- если без диаграммы читатель вынужден держать в голове
  ветвления или параллельные пути.

**Тип — по задаче:**
- `flowchart` — алгоритмы, каскады, fallback-цепочки;
- `sequenceDiagram` — взаимодействие слоёв, вызовы API;
- `stateDiagram-v2` — состояния и переходы;
- `classDiagram` — структура классов, если она неочевидна;
- `erDiagram`, `gantt`, `gitGraph` — по необходимости.

**Правила оформления:**
- Диаграмма — в том же документе, рядом с описываемым
  разделом. Не в отдельном файле.
- Подпись над диаграммой: одно предложение — что она
  показывает.
- Если диаграмма дублирует текст дословно — оставить
  что-то одно. Обычно текст сокращается до 1-2 предложений
  контекста, детали уходят в диаграмму.
- Не вставлять диаграмму «для красоты»: только если она
  несёт информацию.

**Ограничения ассистента (учитывать при генерации):**
- Mermaid-синтаксис пишется «вслепую» — рендер не проверяется.
  Если результат отрендерится криво, пользователь сообщит.
- Точное позиционирование недоступно — раскладка на Mermaid.
- Для графов >15 узлов возможна тесная раскладка — дробить
  на несколько диаграмм.

**Запрещено:**
- Рисовать диаграммы, которые дублируют текст без потери
  информации (ничего не добавляют).
- Переделывать существующие документы ради добавления
  диаграмм вне задачи — только при касании документа.

**Источник правила:** пользователь (сессия 2026-10-12),
постепенное обогащение документации без срочного переписывания.

<a id="project-docs-mobile"></a>
### [AGENTS] project-docs-mobile Пометка о мобильной работе
<a id="project-docs-mobile"></a>
Каждая задача в `docs/ROADMAP.md` получает **пометку о
возможности закрытия с телефона** — сразу после заголовка
`##`, до поля «Статус».

**Рабочее окружение на телефоне:** proot-окружение Ubuntu
в Termux. Доступны полноценный терминал, `git`, `grep`,
`sed`, текстовые редакторы (nano/vim), установка пакетов.
**Недоступны:** Android Studio, эмулятор, локальный запуск
Gradle-сборки (тяжело для proot, нестабильно). ADB
технически возможен (Wi-Fi / USB-OTG), но **способ доставки
собранного APK с телефона на устройство пока не отработан** —
до этого live-тест с телефона не выполняется.

**Замена локального гейта:** локальный Gradle-гейт
заменяется **CI `gate` на PR**. Если правки `.kt`/`.kts`
компилируются на CI, задача закрывается с телефона. Сборка
и тесты локально **не нужны** — это не причина «невозможно».

**Формат:**

    **Мобильная работа:** полное закрытие | частичное | невозможно

**Значения:**

- **полное закрытие** — задача закрывается целиком с
  телефона через proot + PR: правки кода, документации,
  конфигов, `git`, push, PR через web; гейт — CI `gate`.
  Локальная сборка и IDE не нужны.
- **частичное** — часть задачи требует **live-теста**:
  устройство, эмулятор, визуальная проверка UI на девайсе,
  проверка на реальных данных (AppMetrica, реальный счёт).
  В скобках — что именно: `частичное (live-тест UI)`,
  `частичное (live-тест 8 комбинаций тумблеров)`.
  ADB на телефоне технически возможен, но доставка APK с
  телефона не отработана — до этого live-тест считается
  невыполнимым с телефона.
- **невозможно** — задача по своей природе **есть
  live-тест** и не имеет не-live части, которую можно
  закрыть с телефона. Единственный случай сейчас —
  `Live-test Broker lifecycle API: BCS/Finam`.

**Зачем:** «сборка + тесты» — не причина откладывать на
десктоп: CI `gate` покрывает то же. «Невозможно» — только
там, где результат виден лишь на устройстве. При появлении
способа доставки APK с телефона (ADB) `частичное
(live-тест)` станет `полное` — пометки пересмотреть.

**Правило распространяется на все новые задачи.** Закрытые
задачи (`### ✅`) — история, пометки в них **не
пересматриваются** (уточняются только при явной
необходимости, отдельным коммитом).

**Правило распространяется на все новые задачи.**
Существующие задачи размечаются при первом касании
(по правилу обогащения документации — см. «Диаграммы
в документации»).

### [AGENTS] project-docs-section-order Порядок секций в плановых документах
<a id="project-docs-section-order"></a>
В `docs/ROADMAP.md` и `docs/ci-roadmap.md` — два раздела с разной
сортировкой:

**Планируемые задачи:** порядок выполнения (приоритет) — сверху вниз.
Первая задача — следующая к выполнению. Новая задача вставляется в
позицию по приоритету относительно существующих, не в начало раздела.
Существующие задачи, оказавшиеся ниже по приоритету, сдвигаются вниз.
Правило «свежее сверху» не действует: позицию определяет приоритет,
не свежесть создания.

**Завершённые задачи (архив):** свежие — снизу. Линейная
хронологическая лента, читается сверху вниз от старых к новым. Новое
закрытие дописывается в конец файла.

**Зачем разные:** планируемые — рабочий список, частота обращения
высокая. Завершённые — архив, читается редко и целиком (для контекста).

Разделители между блоками и правила переходов описаны в
`docs/docs-structure.md` (§4). Таблица переходов упразднена:
разделители производные, генерируются автоматически.
