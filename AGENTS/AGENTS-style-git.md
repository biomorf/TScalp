### [AGENTS] r5g Работа с задачами в ROADMAP
**Куда коммитить документацию.** Документация проекта
делится на три категории по связи с задачей. Порядок
коммита — по правилу 5b (правка + готовое сообщение в
одном ответе).

1. **Связанная с feature/bugfix** — KDoc новой функции,
   изменения в справочниках, если фича их затрагивает.
   Куда: feature-ветка, коммит `docs(<scope>): <описание>`.

2. **Не связанная ни с одной задачей** — правка
   документации вне контекста задачи: справочники,
   структурные изменения, планирование.
   Куда: прямой push в `dev` (см. «Глобальная
   документация — прямой push в `dev`» ниже).

3. **Срочное мелкое** — фикс опечатки, правка заголовка.
   Куда: bypass для Repository admin, прямой push в `dev`.
   Если появится второй разработчик без bypass — правило
   пересматривается.

**Глобальная документация — прямой push в `dev`.**
К `dev` напрямую (bypass Repository admin) идут
документы вне контекста конкретной задачи:

- `AGENTS.md` — директивы ассистента;
- `README.md` — обзор проекта;
- `docs/ROADMAP.md`, `docs/ci-roadmap.md` — планы;
- `docs/ISSUES.md` — известные проблемы;
- справочники `docs/*.md` — streams, brokers,
  release-process, repo-protection, git-flow и т.п.

Ветки `docs/<topic>` не используются.

Почему:

- **Единая область видимости.** Документация — общая
  картина для всех. Ветка `docs/<topic>` прячет правку
  до merge, остальные видят устаревшую версию.
- **Нет ревьюера.** Второй разработчик не знает
  контекста принятых решений, PR-цикл — задержка без
  пользы.
- **Для `AGENTS.md` — срочность.** Правило, найденное
  в сессии, должно применяться сразу, а не после merge.

При появлении второго разработчика, работающего с
ассистентом, — пересмотреть: возможно, для отдельных
типов документов понадобится review.

**Особый случай: `docs/ROADMAP.md` и `docs/ci-roadmap.md`.**

Планы — глобальная сущность. Плановые правки (новая идея,
перестановка приоритетов, пересмотр формулировки) — это
категория 2. Feature-ветки их не таскают.

**Исключение — метаданные о ходе работы над задачей.** Старт
и завершение задачи — часть самой задачи, идут в feature
(см. жизненный цикл ниже).

**Структура файлов:**

- Задачи живут в `ROADMAP-{wip,plan,defer,done}.md` по статусу;
  `## Планируемые задачи` / `## Закрытые` остались только как ссылки.
- `*-ARCHIVE.md` — **легаси, только чтение**: ассистент в них не пишет и в
  контекст не загружает. Терминальное состояние задачи —
  `ROADMAP-done.md` / `ci-roadmap-done.md`.

**Операции жизненного цикла — только скриптами.** Создание, перенос
между статусными файлами и закрытие задачи выполняются командами из
`AGENTS/scripts/`, inline-код для них запрещён:

| Операция | Команда |
|---|---|
| создать | `docs_add.py --file <статусный файл> --id t-N --title "[TOKEN] T-N <title>" --body-file <f> --at-end --apply --no-rebuild` |
| перенести (start / defer) | `docs_cut.py --file <источник> --id t-N --apply --no-rebuild`, затем `docs_add.py --file <цель> …` |
| закрыть (mark done) | тот же перенос в `ROADMAP-done.md`; `[DONE]` и `**Статус:** выполнено` ставит `docs_normalize.py --apply` |
| после любой операции | `docs_rebuild_index.py --apply`, затем `docs_lint.py --all` |
| проверить состояние | `docs_lint.py --task T-N` |

Синхронность индекса с файлами проверяет гейт: если блок перенесли, а
`docs_rebuild_index.py` не запустили, `docs_lint.py` падает.

**Если нужной операции нет в README.** Ассистент не выбирает сам — он
предлагает пользователю два варианта:

1. **Расширить существующий скрипт или добавить новый** (предпочтительно):
   зафиксировать в `AGENTS/scripts/README.md`, затем выполнять.
2. **Выполнить разово inline** — только по явному решению пользователя.

Inline без выбора допустим только для разовой диагностики, которая ничего
не меняет.

**Причина:** 2026-11-21 закрытие T-44 и T-2 сделано inline-скриптом — 5g
применена «по интерпретации», линтером не проверялась, запись ушла в
архив, который является легаси.

**Жизненный цикл задачи:**

1. **Создание** (руководитель). Задача добавляется в
   `## Планируемые задачи`, статус «запланировано», поле
   «Мобильная работа» заполнено. Коммит в `dev`:
   `docs(roadmap): plan <task>`.

2. **Старт** (исполнитель). Коммит в `dev`:
   `docs(roadmap): start <task>`. Поле «Статус» меняется
   на «в работе», добавляется строка `**Ветка:** feature/<name>`.

3. **Работа** (исполнитель). Feature-ветка создаётся от
   `dev`. Коммиты по коду — обычные, ROADMAP не трогается.

4. **Завершение** (исполнитель). Финальный коммит в
   feature-ветке: `docs(roadmap): mark <task> done`.
   Секция переносится из файла статуса (`ROADMAP-{wip,plan,defer}.md`)
   в `docs/roadmap/ROADMAP-done.md`. Токен `[DONE]` и
   `**Статус:** выполнено` проставляет нормализатор по имени файла —
   вручную править не нужно. Архив не используется.

   **Clean-audit обновляется вместе с mark done.** При
закрытии задачи (`docs(roadmap): mark <task> done`) — проверить
`docs/clean-audit.md` на связанные записи и обновить их в том
же коммите или отдельным docs-коммитом в той же сессии.

- **Исправлено:** статус → `исправлено`, запись переносится
  в раздел `### Исправленные (L<N>)`, добавляется ссылка на
  задачу.
- **Частично:** статус → `частично исправлено`, в записи —
  что именно исправлено, что осталось; ссылка на задачу.
- **Расширено:** статус остаётся `открыто`, в записи —
  уточнение (сколько файлов/вызовов было и стало, что
  добавилось). Ссылка на задачу-источник расширения.
- **Не затронуто:** запись не меняется.

Если запись ссылается на задачу, которая ещё не смержена
(feature-ветка или PR), — статус `исправлено (merge pending
<task>)`; после merge — обновить до `исправлено` и перенести
в `Исправленные` отдельным docs-коммитом.

**Причина:** clean-audit — инвентаризация находок. Если задача
закрывает находку, а запись остаётся `открыто` —
инвентаризация врёт. Следующая сессия видит устаревший статус
и тратит время на проверку «а точно ли открыто?».

**Не путать с 2c.** 2c — про то, что каждая находка заводится
отдельной записью. Это правило — про то, что запись
закрывается вместе с задачей, которая её закрыла.

**Схема полей при переносе в архив:**

   - `**Ветка:**` — **удаляется** (задача смержена).
   - `**Статус:**` — **удаляется** (в закрытой задаче неактуален).
   - `**Дата закрытия:**` — **добавляется** (ISO-8601, `<today>`),
     **сразу после заголовка** `### ✅ <Название>`, до
     `**Мобильная работа:**`. Дата — первое, что видит читатель
     закрытой задачи; других полей до неё быть не должно.
   - `**Подтверждение:**` — **не удаляется**. Переписывается в
     прошедшее время: `**Подтверждение:** выполнено (<дата>,
     <результат>)`. Служит историей — что и когда подтвердили.
   - `**Следующий шаг:**` — **не удаляется**. Переписывается в
     прошедшее время: `**Следующий шаг:** выполнен — <что было>;
     следующий — <актуальный>`. Служит историей навигации.
   - `**Текущее состояние:**` — **переписывается честно**, без
     сокращений: в позитив, если задача закрыта, или удаляется,
     если перекрывается `**Что сделано:**` + `**Подтверждение:**`.
     Сокращать содержимое запрещено (Q-S1 → «не сокращать»).

   **При переносе между блоками содержимое не сокращается.**
   Все блоки секции (`**Контекст:**`, `**Важно:**`,
   `**Предусловия:**`, `**Файлы:**`, `**Шаги:**`, `**Тесты:**`,
   `**Референсы:**`, `**Ограничения:**`, `**Критерий готовности:**`,
   `**Оценка:**`, `**Зависимости:**`, `**Связанные задачи:**`,
   `**Планировали / Сделали:**`, `**Что сделано:**` и т.д.)
   переносятся дословно. Добавлять уточнения — можно.
   Удалять/сокращать — нельзя.

   **Исключение — задачи с пост-релизным подтверждением.**

   **Исключение — задачи с пост-релизным подтверждением.**
   Если результат нельзя проверить до релиза (AppMetrica,
   метрики, live-наблюдение) — mark done в feature-ветке
   **не делается**. Секция остаётся в `## Планируемые
   задачи`, `**Статус:**` меняется на `**Статус:** в работе`,
   и добавляется строка:

       **Подтверждение:** ожидает (<причина>, <deadline>;
       критерий: <как проверять>)

   Пример:

       **Подтверждение:** ожидает (AppMetrica, 2–3 дня
       после релиза; критерий: нет новых fatal
       `io.grpc.StatusException`, появились non-fatal
       `"Unhandled gRPC"`).

   После подтверждения — `docs(roadmap): mark <task> done`
   в `dev` (docs-only), пометка `**Подтверждение:**`
   снимается.

5. **Приёмка** (руководитель). Merge PR = принятие. После
   merge в `dev` задача уже в `docs/roadmap/ROADMAP-done.md`
   (перенос сделан feature-веткой). Отдельного коммита
   после merge **не делается**.

6. **Отклонение** (руководитель). Редкий сценарий. PR
   отклоняется, коммит в `dev`:
   `docs(roadmap): return <task> to work` (или
   `abandon <task>`, если задача отменяется). Задача
   возвращается в `## Планируемые задачи` со статусом
   «в работе» и сохраняет `**Ветка:**`.

**Разделение ролей:**

- **Исполнитель** не ставит статус «принято». Он доводит
  задачу до готовности: финальный коммит переносит её
  в `docs/roadmap/ROADMAP-done.md`. Это декларация «готово к приёмке».
- **Руководитель** подтверждает приёмку фактом merge.
  Если merge не сделан — задача не принята.

**После GitFlow** (см. `docs/ci-roadmap.md` → «Переход на
полный GitFlow») этот регламент переносится в
`docs/git-flow.md` и дополняется спецификой release- и
hotfix-веток.

### [AGENTS] r5f-freeze Ожидание merge: заморозка feature-ветки и dev
С момента создания PR и до его merge — feature-ветка
**заморожена**. Новые коммиты в неё запрещены (даже doc-only,
даже мелкие фиксы).

**Почему:** если ветка меняется после открытия PR, а в
Rulesets включена опция «Require branches to be up to date
before merging», GitHub пересчитывает merge-статус и
перезапускает CI. Это тратит минуты и ломает поток.

**«Момент merge» определён явно.** Merge считается завершённым,
когда одновременно: (а) merge-коммит в `origin/dev`, (б) CI
`gate` на нём зелёный, (в) пользователь подтвердил «PR смержен».
До выполнения всех трёх — **`dev` тоже заморожен**: никаких
коммитов в `dev`, даже docs-only, даже `AGENTS.md`, даже если
merge-коммит уже появился в `origin/dev`. Причина: локальный
`dev` разойдётся с `origin/dev`, и post-PR чек-лист (5f,
`merge --ff-only`) упадёт. Правки — только в рабочем дереве
(unstaged/staged), проверенные 5a/4h, в stash до post-PR.

**Инцидент 2026-10-30:** `AGENTS.md` закоммичен в `dev`
(`b10c790`) до завершения merge PR #75 — история разошлась
(ahead 1 / behind 1). Правило уточнено: «момент merge» — три
условия, `dev` заморожен до всех трёх.

**Что можно во время ожидания:**
- Обсуждать задачу, планировать, читать код.
- Делать правки **прямо в `dev`**, но **без коммитов** —
  оставлять в рабочем дереве (unstaged/staged).
- **Готовить документы** (`docs/`, `AGENTS.md`,
  `AGENTS-LESSONS.md`) — правки в рабочем дереве, без
  коммитов. **Проверить 5a/4h сразу, до stash**: `git diff --check`,
  двойные `---` (awk), чётность fence'ов, line-anchored
  post-checks. В stash — **уже проверенное**; после post-PR
  (5f) — только `stash pop`, замена `merge pending` → `PR #NN`
  и коммит обычным порядком (5b, 5g категория 2). Не откладывать
  проверку на post-PR: между stash и pop `dev` может уйти вперёд,
  проверка «на потом» — лишний риск.
- **Готовиться к следующей задаче (read-only)** —
  диагностика, `grep`, чтение кода, варианты, рекомендация;
  без правок и без коммитов. Правки — только после post-PR
  и создания новой feature-ветки.

**Почему не сидеть без дела:** ожидание CI и merge —
бесплатный слот для документации и подготовки. Правки в
рабочем дереве не нарушают заморозку feature-ветки (не
коммитятся) и не влияют на CI PR.

**Post-PR чек-лист (5f) учитывает это:** первый шаг —
`git stash` (спрятать правки), потом `git checkout dev` и
`git merge --ff-only`, затем `git stash pop` (вернуть правки
и закоммитить их обычным порядком).

<a id="r5f"></a>
### [AGENTS] r5f Post-PR checklist
После сообщения пользователя «PR смержен» / «MR смержен» /
«merged» ассистент **обязан**:

1. **Остановиться.** Не переходить к следующей задаче,
   не предлагать «следующий шаг».
2. **Выдать чек-лист post-PR** (см. ниже) и ждать
   подтверждения пользователя по каждому пункту.
3. Только после выполнения чек-листа — переходить к
   следующей задаче.

**Чек-лист post-PR — скриптом** (r4j: использовать, не переписывать).
Вызов — тоже bash-блок: **оборачивать по `4i` шаблон 1** (`bash << 'BASH_END'`,
`tee "$HOME/deepseek-chat.txt"`, `RC`, `wc`, `exit`), не bare-строкой.

    bash AGENTS/scripts/post-pr.sh <branch> --task T-N

`<branch>` — имя смерженной feature-ветки; `--task T-N` — опционально
(проверить: блок `[DONE] T-N` в `ROADMAP-done.md`, или
`**Подтверждение:**` в `ROADMAP-wip.md`). Без `--task` ROADMAP-шаг
пропускается с подсказкой.

**Что делает скрипт** (справка для чтения, не для копирования):

```bash
git stash 2>/dev/null || echo "nothing to stash"    # 1
git checkout dev                                    # 2
git remote update
git merge --ff-only origin/dev
git stash pop 2>/dev/null || echo "nothing to pop"  # 3
git branch -d <branch>                              # 4
git push origin --delete <branch>                   # 5
sleep 2                                             # 6
git branch -r | grep <branch>                       # 7
git status                                          # 8
# + --task T-N: ROADMAP check (DONE in *-done / Подтверждение in wip)
```

Если `grep` в шаге 7 нашел ветку (несмотря на `sleep 2` и успешный push --delete), это скорее всего кэш локального репозитория. Выполнить `git remote prune origin` и проверить `git branch -r` еще раз.

9. **ROADMAP (если `--task` передан):** скрипт проверяет
   состояние задачи:
    - **обычная задача**: блок `[DONE] T-N` в `docs/roadmap/ROADMAP-done.md`
      (перенос сделан feature-веткой по 5g п.4);
    - **задача с пост-релизным подтверждением**: в `ROADMAP-wip.md`,
      в блоке задачи есть строка `**Подтверждение:**` (см. 5g п.4,
      исключение для deferred closure).
10. Если ни того, ни другого — скрипт падает с `ERROR: mark done
    missing for T-N`. Фикс — **сразу в `dev`**, отдельным коммитом
    `docs(roadmap): mark T-N done`. Не откладывать на следующую сессию.

**Формат ответа ассистента после «PR смержен»:**

    PR смержен. Выполняем post-PR чек-лист:

    bash AGENTS/scripts/post-pr.sh <branch> --task T-N

    Останавливаюсь. Жду вывода.

    Это исключение из 4b: чек-лист выдаётся одним блоком,
    остановка одна — после последней команды. Полный список
    исключений — в 4b.

**Запрещено:**

- Пропускать post-PR чек-лист «потому что очевидно».
- Объединять его с началом следующей задачи.
- Выдавать «следующий шаг» до выполнения чек-листа.

**Причина:** post-PR гигиена — не часть продуктивной
работы, а обязательный ритуал синхронизации. Без
формального чек-листа шаги выпадают из внимания
и накапливаются расхождения между локальной и
удалённой историей.

<a id="r5e"></a>
### [AGENTS] r5e Самодостаточность планов
Любой план, зафиксированный в `docs/ROADMAP.md`,
`docs/ISSUES.md` или в коммите типа
`docs(roadmap): plan ...`, должен быть
**самодостаточным**: другой ассистент (человек или агент)
без доступа к истории чата обязан уметь его реализовать
по одному только описанию.

**Обязательные поля записи:**

- **Статус:** запланировано / в работе / отложено.
- **Контекст:** зачем задача, какую проблему решает.
- **Соответствие Clean:** соответствует | отклонение по 2c
  (принято) | отклонение (открыто). Обязательно для каждой
  задачи, независимо от источника (clean-audit или нет).
- **Нарушенное правило Clean:** одна строка. Для
  «соответствует» — «—».
- **Clean-альтернатива:** как правильно, с плюсами и
  минусами. Для «соответствует» — «—».
- **Выгоды (для «отклонение по 2c»):** что даёт текущий
  вариант — конкретно. Для остальных статусов — «—».
- **MVVM:** соответствует | `M<N>` — <что нарушено>. Для
  не-presentation задач — «— (не применимо)».
- **KMP:** соответствует | блокер — <категория>: <что именно>.
  Для задач вне domain — «— (не применимо)».
- **Предусловия:** что должно быть сделано до начала
  (какие задачи, какие обновления SDK, какие санкции).
- **Файлы:** конкретные пути и классы, которые будут
  затронуты. Если файл ещё не создан — указать, где
  его создать.
- **Шаги:** пронумерованная последовательность действий.
  Один шаг — одно логически завершённое изменение.
- **Референсы:** ссылки на SDK, официальную документацию,
  примеры в репозитории, related-файлы в самом проекте.
- **Ограничения:** что нельзя делать, известные грабли,
  антипаттерны, которых избегаем.
- **Критерий готовности:** как проверить, что задача
  выполнена (какое поведение должно наблюдаться,
  какие тесты должны проходить).
- **Оценка:** время в часах или минутах.
- **Зависимости:** какие задачи блокируют эту,
  какие блокируются этой.
- **Открытые вопросы:** факты, которых не хватает
  для реализации (имя метода, формат сообщения,
  состав полей proto). Каждый — с указанием, где
  искать ответ.

**Clean-, MVVM- и KMP-поля обязательны для каждой задачи**
(2e). Незаполненное поле — сигнал сделать проверку и заполнить.
Правило действует для задач в `docs/ROADMAP.md` и
`docs/ci-roadmap.md`. Для записей в `docs/ISSUES.md` эти поля
не требуются — проблемы описывают симптом, а не план
реализации (проверка для них не применима).

**Запрещено в описании плана:**

- Ссылаться на «как обсуждали в чате», «см. выше»,
  «тот же подход, что для задачи X».
- Оставлять шаг без указания файла, в котором он
  делается.
- Указывать в «Референсах» URL без пояснения, что
  именно там смотреть.
- Формулировать шаги в стиле «доработать каскад» без
  конкретики — что именно и где.

**Правило действует для всех документов проекта.**

<a id="r5d"></a>
### [AGENTS] r5d Жизненный цикл задачи
Для задач, зафиксированных в ROADMAP, применяется
трёхфазный цикл.

**Фаза 1 — открытие.**

Ответ содержит блоки 1–3 (диагностика, варианты,
рекомендация). Ассистент **ждёт утверждения** от
пользователя. Только после «да» — коммит:

    docs(roadmap): plan <название>

В теле: что планируется, зачем, варианты, выбранный подход,
оценка.

**Фаза 2 — реализация.**

Начинается **после** коммита плана. Каждый шаг — блоки 4–6
(правки, коммит, порядок). Между шагами — сборка (п. 4).
Один логически завершённый шаг — один коммит.

**Тесты — часть реализации.**

Если задача добавляет или меняет код с проверяемыми
инвариантами (мапперы, fallback-логика, обработка ошибок,
бизнес-правила) — тесты пишутся в **той же** feature-ветке.
Обычно — последним коммитом Фазы 2, после стабилизации кода.
При TDD или когда тест пишется для каждого метода — возможно
вместе с кодом. Ключевое: тест в ветке **до** `mark done`,
не в отдельном PR после merge.

Порядок для «код + тесты вместе»:
1. Фаза 2: код, зелёный гейт.
2. Фаза 2: тесты на новую логику, зелёный гейт.
3. Фаза 3: `mark done`.

**Почему не отдельным PR:** двойной gate, двойной review,
двойной merge. При соло-разработке — overhead без пользы.
Отдельный PR «только тесты» оправдан лишь когда тесты
дописываются к уже смерженному коду — тогда это **отдельная
задача** в ROADMAP с обоснованием, а не хвост текущей.

**Отложенные тесты фиксируются явно.** Если тест невозможно
написать сейчас (нужна mock-инфраструктура, нужен рефакторинг,
JVM-тест невозможен без Robolectric) — это **не «забыли»**,
а осознанное решение:
- в теле `mark done` коммита — явная фраза «покрытие тестами
  отложено: <причина>»;
- отдельной задачей в ROADMAP — с критерием готовности.

Молча не откладываются.

**Проверка затронутых файлов.**

При написании тестов — пройтись по *затронутым* файлам,
а не только по изменённым строкам. Если в файле есть
публичная функция/класс, которые не тестировались до задачи,
но теперь участвуют в новом потоке данных (вызываются из
нового кода, зависят от него, разделяют с ним инварианты) —
оценить, нужен ли им тест.

**Критерий «добавлять или записывать»:**
- **Тривиальный тест** (5–10 минут, чистая функция, нет
  mock-инфраструктуры) и напрямую проверяет новый инвариант
  — добавить в текущий PR.
- **Отдельная сущность** (нужна mock-инфраструктура, >10 минут,
  свой класс/модуль) — записать в `docs/ISSUES.md` как
  отдельную задачу. Не раздувать PR текущей задачи.

Цель: не пропустить «соседний» пробел, но и не смешивать
в одном PR несколько задач.

**Фаза 3 — закрытие.**

Финальный коммит по коду (если ещё не сделан). Затем коммит
в ROADMAP:

    docs(roadmap): mark <название> done

Секция переносится в `docs/roadmap/ROADMAP-done.md`; токен `[DONE]` и
`**Статус:** выполнено` проставляет нормализатор по имени файла.

Отменённые задачи:

    docs(roadmap): mark <название> cancelled

Причина — в теле коммита.

**Тривиальные задачи** (одна строка, опечатка, правка
параметра) — цикл не применяется. Один коммит.

**Пример:**

1. Ответ: диагностика + варианты A/B + рекомендация A.
2. Пользователь: «A».
3. Коммит `docs(roadmap): plan <задача>`.
4. Ответ: правки «было → стало», коммит `chore(...): ...`.
5. Ответ: правки, коммит.
6. Коммит `docs(roadmap): mark <задача> done`.

<a id="r5b"></a>
### [AGENTS] r5b Правки в docs — сразу с коммитом
Любая правка в `docs/` или `AGENTS.md` сопровождается готовым
сообщением для коммита в том же ответе ассистента. Не отдельным шагом «скажи, когда
закоммитишь», не «пришлю сообщение позже».

Формат ответа для каждого документа — **один блок**:

1. Файл, было/стало.
2. Готовый commit message — **одной командой**, готовой
   к вставке в терминал (см. ниже).
3. Одна строка — что делать дальше.

**Commit message — только скриптом.** Правки `.md`/`.yml`/
`.kt`/`.kts` — через скрипт (4c). Commit message — тоже
текст, который пользователь вставляет в терминал. Голый
текст в чате для копирования через экран телефона —
запрещён, по той же причине, что и ручной копипаст
markdown: опечатки, переносы, потеря строк.

Формат — heredoc через `git commit -F -`:

    git add <files>
    git commit -F - <<'MSGEOF'
    <type>(<scope>): <краткое описание>

    <тело: что изменилось и почему>
    MSGEOF

`git add <files>` — обязательный первый шаг, файлы
перечисляются явно. `git add .` / `git add -A` /
`git add -u` — запрещены: подхватывают лишнее из
рабочего дерева.

Одна команда, копируется целиком, вставляется в терминал
как есть. Тот же приём — для `git tag -a` (через `-F -`)
и для `git commit --amend` (если правка исправляет
незапушенный коммит).

**Pre-check на кириллицу — строго перед `git commit`.** Сразу
перед `git commit -F` (и `git tag -a -F`) — обязательная
проверка `$HOME/.msg.txt`:

    if grep -P '[А-Яа-я]' "$HOME/.msg.txt"; then
      echo "ERROR: Cyrillic in commit message — abort, rewrite"
      exit 1
    fi
    git commit -F "$HOME/.msg.txt"

`grep` вернул 0 (нашёл) → abort, переделать сообщение в
скрипте. `grep` вернул 1 (не нашёл) → OK, продолжаем.
Причина: «Язык коммитов — только английский» (5), но в сессии
2026-11-04 commit message на русском прошёл в `dev` 4 раза
(`c855ebe`, `7294c9b`, `aa7909f`, `55ca55d`) + 1 на feature
(`1bfc359`). Pre-check перед коммитом поймал бы все 5 до
записи в git.

**Идентификаторы clean-audit — латиница в commit/PR.** В
`.md` файлах — `Н5`/`Н94` (кириллическая «Н», как в
clean-audit). В commit message / PR title / PR body — `H5`/
`H94` (латинская «H»). Иначе `grep -P '[А-Яа-я]'` ложно-
срабатывает на кириллическую «Н» в ID.

Heredoc-обёртка — обязательна для всех коммитов, в том
числе когда тело короткое. Визуально удобно: граница
MSGEOF отделяет сообщение от следующих команд, копируется
без захвата лишнего.

Если правится несколько документов (`AGENTS.md` +
`docs/ROADMAP.md`, `docs/ROADMAP.md` + `docs/ISSUES.md`
и т.п.) — **отдельный блок
на каждый документ**, каждый со своим commit message.
Это разные задачи, коммиты не смешиваются.

Запрещено выносить commit message в отдельный блок
ответа — «сначала все правки, потом все коммиты».
Правка и её коммит — атомарная пара.

Правило действует для всех документов проекта.

<a id="r5a"></a>
### [AGENTS] r5a Порядок коммита: локально vs CI
**Локальные изменения** (код, ресурсы, Gradle-конфиги, документация):
коммит **после** зелёного полного гейта (см. ниже).
Если гейт падает — сначала фикс, потом коммит.

**Перед открытием PR — полный гейт.** Минимум
`testDebugUnitTest` недостаточен: CI прогоняет `fast-check`
(unit + lint + ktlint + detekt + Roborazzi verify). Все задачи должны
быть зелёными **до** открытия PR (локально или на CI —
см. «Локальный гейт и CI гейт равнозначны»). Иначе
lint/ktlint/detekt падают на PR — как было в сессиях
2026-10-20/21: ktlint на
`TInvestPositionsWsMapper.toAmountOrZero` и
`TInvestOrderStateWsMapper.toDoubleOrNull`, detekt
MagicNumber в `StreamCombinators`.

**WIP-коммиты — только mobile (proot).** Маркер означает, что
коммит **не компилируется** (локальный Gradle недоступен). На
desktop (Bluefin) каждый коммит требует прохождения полного
локального гейта (`testDebugUnitTest / lintDebug / ktlintCheck /
detekt / Roborazzi verify`). Исключения (WIP на desktop) — только
по явному запросу.

**PR — только при зелёном CI.** Открытие PR (mobile или desktop) —
только после зелёного CI `gate` на последнем коммите
feature-ветки. Desktop: полный локальный гейт обязателен до
коммита; CI `gate` на PR — подтверждение.

**Push в feature — перед PR (4f).** В feature-ветке на
desktop push не после каждого коммита, а один раз перед
открытием PR (`git push origin feature/<name>`). CI `gate`
на финальном коммите — required check PR. Post-push verify
(п. «Post-push проверка защищённых веток») — для `dev` /
`master`, не для feature.

Команда (скрипт):

    bash AGENTS/scripts/run-local-gate.sh
    # для новых тестов / подозрения на кэш:
    bash AGENTS/scripts/run-local-gate.sh --no-build-cache

Скрипт: `:app:clean :app:ktlintCheck :app:lintDebug :app:detekt
:app:testDebugUnitTest -Proborazzi.test.verify=true --continue
--rerun-tasks`, лог — `/tmp/gate.log`, фильтр вывода, exit code = gate.

Ожидаемо: `BUILD SUCCESSFUL`, все гейты зелёные, только
известные warning'и (`statusBarColor`, Gradle 10).

**Локальный гейт и CI гейт равнозначны.** Локальная команда
выше и CI job `gate` (в Rulesets — required check) покрывают
одни и те же четыре задачи: `testDebugUnitTest`, `lintDebug`,
`ktlintCheck`, `detekt`. CI дополнительно запускает
`full-build` (koverVerifyDebug + assembleDebug) — **шире**
локального гейта. Свежий checkout на CI эквивалентен
`clean` локально.

Если CI `gate` на запушенном коммите зелёный — локальный
повтор перед merge **не требуется**. Required check
`gate` технически блокирует merge: PR без зелёного `gate`
не пройдёт, даже если кто-то попытается нажать кнопку.

**Когда CI не заменяет локальный гейт.** Три случая:
1. CI недоступен (нет runner'а, сломана инфраструктура).
2. Задача требует live-теста на устройстве — это только
   локально (см. `docs/live-test.md`).
3. Сработал `paths-ignore` на смешанном коммите (docs + код
   вместе): CI не запустится, но в коммите есть код. В этом
   случае — либо разделить коммиты, либо локальный гейт.

**Оптимизация, не обязательность.** Ошибка стиля или линтера
на PR — это лишний цикл push→CI→fix. Полный локальный
прогон занимает ~50 секунд, дешевле цикла CI. Но если
WIP-коммиты уже запушены и `gate` зелёный — merge разблокирован,
локальный повтор не нужен.

**Исключение: docs-only коммиты.** Если в коммите изменены
**только** `.md` файлы (никаких `.kt`, `.kts`, `.yml`,
`.yaml`, `.xml`, `.gradle`), полный гейт не требуется.
Ни один из четырёх гейтов (testDebugUnitTest, lintDebug,
ktlintCheck, detekt) `.md` не валидирует — прогон 40–50
секунд ради ничего.

Вместо полного гейта для docs-only — **mini-gate** (обязателен
перед docs-коммитом, один shell-блок, ~5 секунд):

    F="docs/ROADMAP.md"   # ← путь к правленому файлу
    git diff --check || { echo "FAIL: trailing ws"; exit 1; }
    echo "OK: trailing ws"
    awk 'prev=="---" && $0=="---" {print "DOUBLE --- at " NR; bad=1} {prev=$0} END{exit bad+0}' "$F" \
      || { echo "FAIL: double ---"; exit 1; }
    echo "OK: no double ---"
    N=$(grep -cE '^(```|~~~)' "$F") || N=0
    test $((N % 2)) -eq 0 || { echo "FAIL: fence parity ($N)"; exit 1; }
    echo "OK: fence parity ($N)"
    for d in $(grep -oE 'docs/[a-zA-Z0-9_./-]+\.md' "$F" | sort -u); do
      test -f "$d" || { echo "BROKEN: $d"; exit 1; }
    done
    echo "OK: all docs/*.md exist"

Четыре пункта markdown-чек-листа, механически: trailing ws,
двойные `---`, fence parity, битые ссылки на `docs/*.md`.
**Все четыре abort'ят** группу (`|| { echo "FAIL: ..."; exit 1; }`):
красный вывод любого пункта = коммит запрещён. Фикс —
отдельным шагом, повтор mini-gate.

Если правок несколько файлов — `F` по одному, mini-gate
на каждый файл отдельно (не склеивать в один проход).

Ручной запуск того же — `python3 AGENTS/scripts/docs_lint.py --changed [files...]` (без аргументов — все изменённые `.md`).

Автоматическая проверка `.md` в CI появится отдельной задачей:
`docs/ci-roadmap.md` → «Markdown linter в CI». До тех пор —
mini-gate выше — **обязательный** шаг перед docs-коммитом.
pre-push hook расширяется на `.md` отдельной задачей
(`docs/ci-roadmap.md` → «Desktop: pre-push hook»).

**CI/CD изменения** (`.gitlab-ci.yml`, CI-скрипты, конфиги пайплайна):
коммит **до** проверки. Пайплайн не воспроизводится локально,
поэтому порядок обратный:
1. внести правку;
2. закоммитить;
3. запушить и дождаться результата пайплайна;
4. пайплайн зелёный → следующий шаг;
5. пайплайн красный → фикс **отдельным коммитом** (не `--amend`,
   не force-push в `master`/`dev`).

**Смешанные изменения** (код + CI в одной задаче) — **два коммита**,
по одному на область. Не смешивать.

**Общий принцип:** один коммит — одна задача. Дробление на этапы
приветствуется, лишь бы каждый коммит был логически завершён и
точка отката была осмысленной.

**Post-push проверка защищённых веток.** После `git push`
в `dev`, `master`, `release/**`, `hotfix/**` —
два обязательных шага:

1. **Проверить, что коммит в origin:**
   `git log --oneline -3 origin/<branch>` + `git status`.
   Ожидаемо: коммит виден, ветка не расходится с origin.
2. **Дождаться зелёного CI** на запушенном коммите.
   Следующий шаг не начинается до результата.

Причина: rulesets не воспроизводятся локально. Push
может пройти, но CI упадёт — и это обнаружится только
на PR следующей задачи, где уже неочевидно, чей это
красный.

Если CI красный — фикс **отдельным коммитом** (не
`--amend`, не force-push).

<a id="r5"></a>
### [AGENTS] r5 Коммит после каждой задачи
Как только задача завершена и проверена (сборка зелёная,
на устройстве работает) — ассистент предлагает коммит с готовым
сообщением в стиле:

`<type>(<scope>): <краткое описание>`

`<тело: что изменилось и почему>`

Типы: `feat`, `fix`, `refactor`, `chore`, `docs`, `test`.

**`wip` — не тип.** Стандартный тип (`feat`, `fix`, ...) ставится
в заголовок всегда.

**WIP-маркер = коммит не компилируется.** WIP-коммиты — только
mobile (proot), где локальный Gradle недоступен. На desktop каждый
коммит требует прохождения полного локального гейта — WIP-маркеров
нет (исключения — только по явному запросу). Env-заметка в теле
(`WIP — mobile (proot), CI gate; not final.` или
`WIP — desktop, not final.`) — **только в WIP-коммитах**.

Пример:

    feat(domain): add OrdersApi role interface

    WIP — mobile (proot), CI gate; not final.
    - Add domain/api/roles/OrdersApi.kt with 6 methods...

**Язык коммитов — только английский.** Заголовок и тело.
Русский в commit message запрещён, даже если обсуждение задачи
идёт на русском.

**Цитаты — тоже на английском.** Если в коммите нужно
сослаться на русскоязычный текст (название правила,
название задачи, сообщение об ошибке, идентификатор из документации),
цитата переводится или перефразируется на английский.
Дословная русская цитата внутри английского текста
запрещена, даже в кавычках.

Пример:
- Запрещено: `Kept branch-side rules: "Одна правка — один
  блок", "Проверочный маркер должен быть уникален".`
- Правильно: `Kept branch-side rules: "One edit, one block",
  "Verification marker must be unique".`

Единственное исключение: если русскоязычный фрагмент — это
код-идентификатор (имя файла, имя поля в коде, точная строка
из `.kt`-файла), который нельзя перевести без потери смысла.
Тогда он остаётся в backticks как код, а пояснение вокруг —
на английском. Пример: `kept field "blocked" as-is`.

**Правило распространяется на все текстовые артефакты
репозитория:** commit message, тело PR/MR, комментарии
в PR/MR, сообщения тегов, release notes, код-ревью.
Всё, что остаётся в истории и доступно другим —
на английском.

Чат с пользователем — на русском (см. «Коммуникация»).
Граница проходит по репозиторию, а не по теме обсуждения.

Коммит — точка отката. Не коммитить «в конце дня» пачкой.

Исключение: если работа идёт с устройства без доступа к
терминалу (телефон, веб-интерфейс GitLab без локального
репозитория) — допустимо накапливать изменения и закоммитить
одним блоком при первой возможности. Такой блок в commit
message должен быть явно разделён на смысловые части в теле
(разделы `- area: ...`), даже если физически это один коммит.

<a id="r4g"></a>
### [AGENTS] r4g Git-команды без дефолтов
**Любая git-команда, которая может использовать значение
по умолчанию, — запрещена.** Правило действует для всех
действий ассистента с git, не только в 4f.

Запрещено и обязательно:

| Запрещено (дефолт) | Обязательно (явно) |
|---|---|
| `git push` | `git push origin <branch>` |
| `git push --tags` | `git push origin <branch> --tags` (если действительно нужны все теги) |
| `git push -u` без адресата | `git push -u origin <branch>` |
| `git add .` | `git add <file1> <file2> …` |
| `git add -A` | `git add <file1> <file2> …` |
| `git add -u` | `git add <file1> <file2> …` |
| `git commit -m "…"` с многострочным текстом | `git commit -F - <<'MSGEOF' … MSGEOF` (5b) |
| `git checkout` без имени | `git checkout <branch>` |
| `git merge` без ветки | `git merge <branch>` |
| `git merge --ff-only` без источника | `git merge --ff-only origin/<branch>` |
| `git pull` | `git remote update` + `git merge --ff-only origin/<branch>` (не pull) |
| `git reset --hard` без указания | `git reset --hard <ref>` (и только после паузы, 4e) |
| `git branch -d` без имени | `git branch -d <branch>` |
| `git tag -a` без сообщения | `git tag -a <tag> -F - <<'MSGEOF' … MSGEOF` |
| `git stash push` без сообщения | `git stash push -u -m "<branch>: <step>"` |
| `git stash pop` без явного «да» | выполняется в блоке 1 или 2 (4f), не самостоятельно |

**Почему:** в проекте два remote (`origin`, `gitlab`),
upstream-tracking может перепутаться после переключений
веток; `git add .` подхватывает untracked-мусор; `git pull`
делает молчаливый merge (см. «Git workflow: синхронизация
с origin»). Явная форма исключает все эти случаи.

**Инцидент 2026-10-27** (invest-repository-split, шаг 5):
`git push` без адресата — отправил бы в upstream (который
мог быть не `origin` и не текущая ветка). Явная форма
`git push origin <branch>` введена после этого.

**Не путать с 4e.** 4e — безопасность shell-команд в
ответах (инъекции, секреты, `grep -q` на Gradle). 4g — про
git-дефолты (адресат, файлы, ветка).

**Не путать с «Git workflow: синхронизация с origin».**
Там — почему `git pull` запрещён для синхронизации
(конкретный паттерн). 4g — общий принцип «без дефолтов»
для любых git-команд.

<a id="r4f"></a>
### [AGENTS] r4f Дорогие операции: правки → гейт → коммит → push
Гейт (`./gradlew ... --rerun-tasks`), коммит и `git push` —
операции с внешними эффектами: 30–60 секунд сборки, трата
Actions-минут, запись в origin. Перед ними — пауза:
пользователь должен видеть состояние до того, как эти
операции запустятся.

**Структура шага (код):**

1. **Блок 1 — правки.** Скрипт правки + верификация +
   `git diff`, в одном shell-блоке (4c). Пауза:
   пользователь проверяет корректность.
2. **Блок 2 — гейт → условный коммит → push.** Один
   shell-блок для копирования целиком. Пауза: пользователь
   возвращает вывод.

**Шаблон блока 2 (обязательный):**

```bash
set -uo pipefail
./gradlew :app:clean :app:ktlintCheck :app:lintDebug :app:detekt :app:testDebugUnitTest --continue --rerun-tasks > /tmp/gate.log 2>&1
GATE=$?
set -e
echo "exit=$GATE"
grep -E '\[warn\]|\[error\]|^w:|^e:|FAILED|BUILD|\.kt:[0-9]+:[0-9]+' /tmp/gate.log
echo "---"
tail -3 /tmp/gate.log

if [ "$GATE" -eq 0 ]; then
  git add <files>
  git commit -F - <<'MSGEOF'
  <commit message>
  MSGEOF
  git push origin <branch>
  echo "PUSHED to origin <branch>"
else
  echo "GATE RED — commit/push skipped"
fi
```

- `<files>` — явный список (4g).
- `<branch>` — имя текущей ветки, вписано **литерально**.
- `<commit message>` — по 5b.

**Push при зелёном гейте — по типу ветки.** Для
`dev` / `master` / `release` / `hotfix` — автоматический
push после зелёного гейта: один round-trip **для блока 2**
(пользователь запускает блок 2 один раз, получает `PUSHED
to origin <branch>` или `GATE RED` без коммита и push).
Для feature (desktop) — **батч перед PR** (см. ниже
«Push в feature-ветке — батч перед PR»). Красный гейт
блокирует коммит и push; фикс — отдельным шагом (4b).

**Push в feature-ветке — батч перед PR (desktop).** На
desktop (Bluefin) в feature-ветке коммиты идут **локально**,
push — один раз, перед созданием PR:

    git push origin feature/<name>

После этого — открытие PR (5f). Причина: push каждого
коммита в feature на desktop — лишние 10–20 сек на шаг,
CI на каждый коммит (Actions-минуты, лишние прогоны gate
для промежуточных состояний). PR гейтит финальное
состояние.

**Исключения — push после каждого коммита:**

- **Mobile (proot)** — CI gate = единственный гейт
  (локальный Gradle недоступен); push после WIP-коммита
  даёт CI-проверку до следующего шага.
- **`dev` / `master`** (docs-only, bypass) — прямой push
  в защищённую ветку, post-push verify (5a) обязателен.
- **`release/*` / `hotfix/*`** — стратегия как у feature
  (батч перед PR в `master`).
- **Запрос пользователя** — «пушни сейчас» переопределяет
  дефолт.

**Исторические push в feature не откатываются.** Если
правило введено после N коммитов, они остаются
запушенными — force-push не делаем.

**Исключение: UI-правки.** Для изменений, видимых
пользователю (правило 1: тексты, иконки, разметка, цвета,
порядок элементов, тема, system bars), блок 2 делится на
два подблока с паузой между ними:

- **2a — гейт.** `./gradlew ...` → `/tmp/gate.log`.
  Пауза: пользователь видит результат (BUILD SUCCESSFUL /
  GATE RED), проверяет diff / поведение.
- **2b — commit + push.** Только после явного «да» /
  «ок» / «принимаю». Пауза: `PUSHED` или ошибка.

Причина: зелёный гейт ≠ «правки корректны». Для UI
пользователь проверяет «стало» глазами; автопуш уводит
коммит до проверки.

Список UI-правок (для этого исключения): `Theme.kt`,
экраны (`*Screen.kt`), компоненты (`*Card.kt`,
`*Dialog.kt`), `themes.xml` / `colors.xml` / `strings.xml`
(видимые пользователю), `AndroidManifest.xml` (theme /
activity attributes). Для docs-only — гейт не нужен,
commit+push после проверки текста (5a).

**Для docs-only** (5a): гейт не нужен. Блок 1 — правка +
verify, пауза (пользователь проверяет изменения). Блок 2 —
`git add <files>` + `git commit -F -` + `git push origin
<branch>`, без дополнительной паузы (проверка уже была
в блоке 1).

**Механизм `git stash` при правке AGENTS.** Если нужно
править `AGENTS.md` (или другой документ категории 2 по 5g)
в `dev`, а в текущей feature-ветке есть незакоммиченные
изменения по другой задаче — **`git checkout dev` без stash
запрещён**: незакоммиченные изменения переедут в `dev`
(инцидент 2026-10-27, `SettingsViewModel`).

Порядок:

1. В feature: `git stash push -u -m "<branch>: <step> (temp)"`.
2. Проверка: `git stash list | head -1` — наш stash сверху.
   Если нет — стоп, разбираться.
3. Проверка: `git status --short` — пусто. Если нет —
   остатки не спрятались, стоп.
4. `git checkout dev` + `git remote update` +
   `git merge --ff-only origin/dev`.
5a. Правка AGENTS + verify. Пауза: пользователь проверяет.
5b. Блок 2: `git add` + `git commit` + `git push origin dev`.
6. `git checkout <feature>` + `git stash pop`.
7. Проверка: `git status --short` — изменения вернулись;
   `git stash list` — наш stash пропал.

**Идемпотентность (4d).** `git stash push` при пустом
рабочем дереве — no-op с «No local changes to save»
(exit 0). `git stash pop` при пустом stash — «No stash
entries found» (exit 1), обработка:
`git stash pop || echo "nothing to pop — already applied?"`.
Если pop конфликтует — **стоп**, разбираться вручную.

**Инциденты 2026-10-27** (invest-repository-split):

- шаг 1 — коммит в `dev` до feature-ветки; исправлен
  `reset --soft` + переносом на feature.
- шаг 5 — `git push` в условном блоке после гейта **без
  явного адресата** (голый `git push`). Концепция условного
  push корректна, дефект — в адресате (4g).
- `SettingsViewModel` — `git checkout dev` без stash при
  незакоммиченных правках; правки уехали в `dev`.

**Не путать с 4b.** 4b — «один шаг за раз, стоп после
каждого». 4f — частный случай: правки → гейт+коммит+push
разнесены на два блока с паузой между ними.

**Не путать с 4c.** 4c — пауза после скрипта правки (файлы
изменены, не закоммичены, гейт не запускался). 4f —
продолжение: после блока 1 идёт блок 2 (гейт → условный
коммит → push).

**Не путать с 4g.** 4g — запрет дефолтов в git (адресат,
файлы, ветка). Действует для всех git-команд ассистента,
не только в блоке 2.
